# YTwins 网页 demo 规格（Spec）

Status: ready-for-agent

> 本 spec 是三轮 interview（术语轮 + 边界轮）与两份调研（`docs/ytwins/parent-voice-principles.md`、
> `docs/ytwins/memory-linking-research.md`）的收束件。术语一律取自 [`CONTEXT.md`](../../CONTEXT.md)，
> 不新造同义词。英文对照件见 [`spec.en.md`](./spec.en.md)。

## 问题陈述（Problem Statement）

我是这个产品唯一的用户。我每天会有一些零碎的东西想顺手丢下来：一句情绪、一个决定、一件要办的事、一个突然
冒出来的灵感。它们不成句、没有格式，而且经常混在同一段话里（比如「老师今天讲了期末怎么算分，好烦」既是
**事项**也是**情绪**）。

现在这些东西的处境是：丢进备忘录就再也不会被回头看，丢进聊天窗口就散了，想攒成任何结论都得先自己整理、
分类、打标签、复盘 —— 而这三件事我一件都不想干。于是结果是：**素材每天都在产生，结论从来没有出现过**。
我甚至不确定自己这半年到底在在意什么。

已有的工具都不解决这个问题：笔记软件要我组织，聊天助手要我当时就对话（它的价值在这一次对话里，不在积累），
任务应用只认「待办」。它们都假设我愿意为工具做整理工作，而我的硬要求恰恰是**不愿意**。

另一层顾虑是：这类「AI 记录我的碎片」的工具，天然让人担心两件事 —— **它在悄悄训练什么**（我是不是在喂一个
我不了解的东西）、和**它会不会拿我的数据去别处**。我需要它对我诚实，也需要我随时能把它删干净。

## 解决方案（Solution）

一个**纯本地、无账号**的网页 demo（将来是手机应用）。我只需要做一件事：把碎片**丢**进去。剩下的三件事由它
在背后完成：

- **接住**：一段无格式的输入丢进来，它自动分出**事项**与**留档**，并从中抽出**词条**（保留我自己的说法），
  同时用**回应方式**给我一句简短的应答 —— 有情绪就先接情绪，没有就不硬凑。
- **沉淀**：我看不见的地方，**词条**之间长出**链接**（语义相近、或出现在同一次**投递**里）。当某个情绪或决策
  与足够多的词条相连，跨过**阈值**，就汇集出一条**小结论**。小结论不断增补、互相修订，形成**画像**与**结论链**。
- **浮现**：只在我**情绪投递**或**主动询问**时，把**小结论**或**碰撞**出的**答案**用不确定的语气浮出来一条。
  措辞强弱与背后的支撑度绑定，同一主题 7 天内只浮一次。

它同时能回答**追溯**问题（「期末怎么算分」→ 准确回答 + 指出源自哪一次投递），并把**事项**落到时间上（**排程**）。
demo 用三个动作证明这条链路成立：**丢** → **问** → **浮**。

它是**陪伴**而不是陪聊：它一直记得我，但不主动冒出来打扰我。我的价值感来自积累，而不是来自对话。

## 用户故事（User Stories）

**投递与接住**

1. 作为用户，我希望把一段没格式、没分类的杂乱输入直接丢进输入框，以便不用先想清楚它属于哪一类。
2. 作为用户，我希望同一段话里既有事情又有情绪时也能一次丢完，以便不用把它拆成两条。
3. 作为用户，我希望投递时不必选类型、不必填时间、不必打标签，以便「丢」这个动作本身不需要任何决策成本。
4. 作为用户，我希望系统自动从投递里分出**事项**与**留档**，以便我事后不必回头整理。
5. 作为用户，我希望**留档**保真保存我的原话（不存摘要），以便日后追溯时看到的是我当时真正说过的话。
6. 作为用户，我希望系统在内部给投递打**输入类型**（情绪/决策/事项/灵感），但全程不让我感知、不要求我选择，
   以便我不用学会它的分类法。
7. 作为用户，我希望从投递里抽出**词条**并保留我自己的说法（是「想学吉他」，不是「音乐兴趣」），
   以便我日后看到的结论仍然是我能认出的语言。
8. 作为用户，我希望每次投递后得到一句简短的**回应**，以便我知道它接住了，而不是丢进了黑洞。
9. 作为用户，我希望**互动**不必每天发生，以便我隔几天来一次产品依然成立、不会催我打卡。
10. 作为用户，我希望投递以后立刻就算成功（原文先落库，抽取慢一点没关系），以便我不想等也不怕丢东西。

**回应方式（parent voice）**

11. 作为用户，我希望输入里有情绪时，它回的第一句是情绪回应，而不是信息、结论、建议或提问，
    以便我先被接住。
12. 作为用户，我希望它替我把感受说出来（「你好像…」「听起来…」），而不是逼我先解释原因，
    以便我不用在难受的时候先做论证。
13. 作为用户，我希望它只描述具体的事情，不给我的人格下定义（包括「正面」的定性），以便我不被贴上标签。
14. 作为用户，我希望它默认不给建议，以便我自己解决问题的过程不被剥夺。
15. 作为用户，我希望它只在我明确问「怎么办」、或我自己已经说出一个方向时给建议，而且最多一条、我可以拒绝，
    以便选择权始终在我手里。
16. 作为用户，我希望它不替我做决定、不替我拍板下一步、不宣布「已经帮我安排好了」，以便我不被架空。
17. 作为用户，我希望它不问「为什么」，以便我不被审问。
18. 作为用户，我希望单轮最多被问一个问题，且它不重复问我已经答过的事，以便对话不变成盘问。
19. 作为用户，我希望我说「不想说 / 算了 / 没事」时它停止追问，只留一句最短的在场声明，以便我保有沉默的权利。
20. 作为用户，我希望它不做未被索取的提醒（作息、喝水、效率、健康），以便关心不是负担。
21. 作为用户，我希望它不把话题转向「开心的事」来盖过我的难受，以便我的感受被当真。
22. 作为用户，我希望它区分「接纳感受」与「认同判断」，以便我既被理解，又不被鼓励停止反省。
23. 作为用户，我希望它的回复默认不超过 3 句话、约 60 字，不用亲昵称呼、不拿语气词充当内容，
    以便回应听起来不像客服也不像唠叨。
24. 作为用户，我希望它不用「但是 / 不过 / 至少」这类转折收尾，以便前半句的接纳不被撤销。
25. 作为用户，我希望它接得不好时直接承认并修正（不解释、不辩护、不长篇道歉），以便关系被修复而不是被表演。
26. 作为用户，我希望它只用中文回应，以便这个产品不摆出外语腔。

**沉淀、链接与结论**

27. 作为用户，我希望**词条**之间自动长出**链接**，以便关联不需要我手工建立。
28. 作为用户，我希望链接包含两种：语义相近（预训练 embedding 的余弦相似度 + 阈值）与同一次投递里共同出现，
    以便既抓住意思上的接近，也抓住「当时是一起说的」。
29. 作为用户，我希望当某个情绪或决策与足够多的词条相连、跨过**阈值**时，自动汇集出一条**小结论**，
    以便结论来自我的积累，而不是来自某一次对话。
30. 作为用户，我希望**阈值**是数量门槛（足够多的词条连上来），不是时间门槛，以便「来了三次」比「过了三天」更有意义。
31. 作为用户，我希望整个**沉淀**过程我看不见，以便我不必参与、也不必理解它的机制。
32. 作为用户，我希望**小结论**是说人话的陈述句（例如「你似乎很想学吉他」），以便我能立刻判断它对不对。
33. 作为用户，我希望**画像**就是小结论的集合本身（不是另一份藏起来的模型），以便它对我没有秘密。
34. 作为用户，我希望小结论后来可以被修订 —— 可以推翻，也可以继承，以便我的成长能被记录下来而不是被冻结。
35. 作为用户，我希望**结论链**默认只读、但我想看就能看，以便我随时知道它为什么会这么想。
36. 作为用户，我希望我能把某条小结论标为「不对」，并让这次否定在链上成为一次**推翻**，以便纠错是一件很轻的事。
37. 作为用户，我希望我能在结论旁边补一句自己的话，并让那句话本身成为一次**投递**，以便我的反馈也进入素材。
38. 作为用户，我希望它没有打分、点赞或批量反馈功能，以便我不被卷进「训练它」的工作 —— 那是无感的红线。
39. 作为用户，我希望每条小结论都能告诉我它是由哪些词条支撑的，以便我不必凭信任接受它。

**浮现与答案**

40. 作为用户，我希望它默认不主动推送，只在我**情绪投递**或**主动询问**时尝试**浮现**，以便它不打扰我。
41. 作为用户，我希望同一主题 **7 天内只浮一次**，以便我不会被同一件事反复念。
42. 作为用户，我希望每轮最多浮出一条，以便浮现是「一句话」而不是「一份报告」。
43. 作为用户，我希望浮现出来的内容一律用不确定语气（「你似乎…」「你最近…」），以便措辞与支撑度一致。
44. 作为用户，我希望措辞的强弱由可解释的数值决定（支撑词条数量、链接强度、时间跨度），
    而不是由模型当场「感觉」一个语气，以便日后能回答我「你当时为什么这么说」。
45. 作为用户，我希望**答案**是多条小结论汇集而成、只可能出自我自己数据的一句话，以便它不给我放之四海皆准的废话。
46. 作为用户，我希望我能直接问「你觉得我最近怎么样」，以便我想要的时候就能拿到一次观察。
47. 作为用户，我希望它在支撑不足时宁可不浮、或明说「我不太确定」，以便它不靠断言烧掉我的信任。

**追溯与排程**

48. 作为用户，我希望对**留档**提问时得到准确的回答，并看到这条答案来自哪一次投递，以便我能核对。
49. 作为用户，我希望召回不足时它直说没找到，而不是编一个听起来合理的答案，以便它值得被信任。
50. 作为用户，我希望**事项**被自动落到时间上（我不用自己填时间），以便排程不额外花我的力气。
51. 作为用户，我希望没解析出时间的事项被保留为「待安排」而不是被丢掉，以便我不丢失任何一件要做的事。
52. 作为用户，我希望能看到即将到期的事项列表，以便我在打开页面时就知道该做什么。
53. 作为用户，我希望 demo 阶段不做系统级推送与提醒可靠性保证，以便先把「接住 → 沉淀 → 浮现」这条链路做对。

**数据、隐私与可维护性**

54. 作为用户，我希望产品纯本地运行、不需要账号，以便它是我自己的东西。
55. 作为用户，我希望删除一次投递时被明确告知「有 N 条小结论是从它来的」，并由我决定是否一起删，
    以便删除既干净又不意外。
56. 作为用户，我希望级联删除之后，追溯与结论里不再残留它的痕迹，以便「删掉」是真的删掉。
57. 作为用户，我希望它明确告诉我哪部分数据会离开这台机器（demo 阶段：送去云端 LLM 的原文），
    以便我能自己做隐私取舍。
58. 作为用户，我希望将来能只改配置就把推理换成完全本地的（Ollama），而不改动领域逻辑，
    以便我可以在隐私与速度之间重新选择。
59. 作为用户，我希望将来做手机端时界面可以整个换掉而不动领域逻辑，以便终局形态不必推倒重来。
60. 作为用户，我希望它不训练任何模型、也不引入图数据库，以便这个项目长期只有我一个人也能维护得起。
61. 作为用户，我希望一年的 API 成本在 1 美元量级，以便成本永远不是我使用它的顾虑。

**demo 三幕**

62. 作为演示者，我希望第一幕「丢」能一次展示：一段含评分标准与一句情绪的杂乱输入，不选类型、不填时间，
    系统自动分出事项与留档。
63. 作为演示者，我希望第二幕「问」以「几天后」的视角问「期末怎么算分」，得到准确回答并看到出处。
64. 作为演示者，我希望第三幕「浮」在再丢一句情绪化输入后，浮出一条不确定语气的小结论，且这条小结论有足够
    的预置词条支撑。
65. 作为演示者，我希望三幕都能在预置数据上稳定、可重复地跑出来，以便演示不靠运气。

## 实现决策（Implementation Decisions）

### 测试 seam（两处）

1. **领域核心的 interface（最高 seam）。** 领域逻辑——投递解析、沉淀、浮现、排程、追溯、回应方式的应用——
   全部收在一个 module 后面，对外只暴露少量任务形状的操作。所有自动化测试都从这个 interface 驱动，
   它也是网页界面层唯一被允许依赖的东西。界面层与存储层都不上 seam。
2. **AI provider port（唯一的外部依赖 seam）。** 一切非确定的外部智能调用都从这个 port 出去：
   - `extract`：把一段投递正文结构化抽取成词条（保留原话）+ 输入类型 + 情绪/决策标记；
   - `embed`：把文本编码成向量（供链接的余弦相似度使用）；
   - `judgeLink`：判定两条词条是否语义相近（只在灰区调用）；
   - `compose`：把支撑结论/词条汇集成一条答案，并给出它自己的置信度；
   - `respond`：在回应方式的约束下生成对一次投递的回应。

   真实实现与假实现可互换。假实现由测试脚本按输入返回预置结果，因此领域测试完全确定。

### modules

- **领域核心**：上述最高 seam 的持有者。内部按职责分为：**投递解析**（投递 → 事项 / 留档 / 词条 + 输入类型）、
  **沉淀**（链接、阈值累加、汇集小结论、画像、结论链）、**浮现**（时机判定 + 冷却 + 措辞分级）、
  **排程**（事项落到时间）、**追溯**（对留档的问答 + 出处）、**回应方式的应用**（把硬约束变成指令与校验）。
  这些内部划分不是 seam，测试不穿透它们。
- **AI provider port**：一个 interface，两个 implementation（真实 / 假）。
- **存储**：本地 SQLite 文件库，承载投递与留档原文、词条、链接、小结论、结论链、事项、浮现记录。
- **界面层**：网页 demo（三幕），只通过领域核心 interface 工作。

### 领域核心 interface 的形状

操作用领域词命名，返回值是**任务形状**（「这次投递接住了什么、回应是什么」），不是存储形状（不暴露表、id
拼装、SQL）。至少包含：

- **丢一次投递**：返回这次投递产生的事项（可以没有）、留档、抽出的词条，以及给用户的那句回应。
- **追溯提问**：返回留档里的**事实**的答复，以及它来自哪一次或哪几次投递；召回不足时返回「没找到」这种明确结果，
  不编造。答的是事实而非**判断**，所以照实陈述，不用不确定语气（术语见 `CONTEXT.md`）。
- **请求一次浮现**：返回零条或一条小结论/答案；零条是正常结果（冷却中、或支撑不足）。
- **读画像 / 读结论链**：只读视图，含每条小结论的支撑词条与它修订/被修订的关系。
- **标一条小结论为「不对」**：在链上记一次推翻，原结论保留。
- **在小结论旁补一句自己的话**：那句话作为一次新投递进入同一条链路。
- **列事项**：按时间列出到期与待安排的事项。
- **预览删除一次投递**：返回「有 N 条小结论是从它来的」这一事实，供用户决定。
- **确认删除一次投递**：按用户的选择级联删除或仅删原文，并使后续追溯/结论不再引用它。

### 数据与算法决策

- **原文全存，不存摘要。** 留档与投递正文是同一份保真内容；事项与词条都指回它们来自哪一次投递。
- **抽取异步于落库。** 投递一进来原文立即落库、立即返回「接住了」；词条抽取即使失败或延迟也不影响投递成功，
  后续可补抽。
- **链接两类**：① 语义相近——词条向量余弦相似度，三段式处理（高分直接连、低分不连、**灰区**调 `judgeLink`
  或先漏连）；② 同次投递出现——零模型的硬边。链接强度可比，且保留连接理由。
- **阈值汇集照抄 Generative Agents 的形状**：跨过阈值就生成一条小结论，并把支撑它的词条一起存下来。
  **阈值是数量门槛**，由一个可配置常量承载，初始值以「demo 第三幕的预置数据必然触发、且不会每次投递都触发」为准。
  > **2026-09-16 更正（05 的 prototype 实测）**：原写法是「给词条一个由 LLM 打的相关度分数，累加」。
  > 实测下来**数的是「这件事被提起过几次」**，不是词条数、也不是相关度分数 —— 否则一句话里塞得词条多就更容易说话。
  > 数值与口径的完整表在 [`issues/05`](./issues/05-conclusion-threshold-portrait-chain.md) 的 `## Comments` 末尾，
  > `CONTEXT.md` 的「阈值」条目已按此改写。这里保留 Generative Agents 的形状（累积 → 跨阈值 → 生成结论 + 存支撑），
  > 只更正「累加什么」。
- **汇集有防抖**：不在每次投递后立刻判定阈值，而是「安静一段时间后」或「累积若干条后」触发，避免几句互为
  上下文的话被过早汇集成错结论。
- **答案的可解释性**：每条答案/小结论都带支撑词条列表；**措辞强弱由可解释数值映射**（支撑词条数量、
  平均链接强度、时间跨度），不是让 LLM 自由选语气。
  > **2026-09-16 更正（05 落地时）**：没有单独一个「置信度」数字 —— 一个标量会把三种不同的证据压成一个
  > 假精确的数。落地的形状是**三档措辞**（弱／中／强）由上面三个数值读出，三个数值本身随结论一起存下来并在页面上可读
  > （「为什么这么说」），所以「说得出为什么」这条仍然成立。
- **不确定语气是硬约束**：只作用于**答案**与**浮现**，不改写普通回应。
- **结论链只增不改**：标「不对」记一次推翻；旧结论不被覆盖或删除（与「原文全存 + 日后追溯」一致），
  因此旧结论需要留存版本与被取代关系。
- **浮现的时机与冷却**：只在情绪投递或用户主动询问时尝试；同一主题 7 天冷却；每轮最多一条。**主题**的工程定义
  是「支撑该结论的词条集合的语义重叠」——重叠超过一个内部比例即视为同一主题。
- **删除级联**：两步——先预览受影响的小结论数量并明确告知，再按用户选择执行；存储层用外键级联保证不留孤儿，
  已删除投递的正文不再出现在任何追溯结果里。

### 回应方式怎么落地

`docs/ytwins/parent-voice-principles.md` 的 15 条「可执行的回应规则」是硬约束，落地方式：

- 可机械判定的那些（句数/字数上限、是否以「为什么」起问、问句数量、禁用词表、转折收尾、亲昵称呼）由**代码校验**，
  不指望模型自觉。
- 校验失败时**重生成一次**；第二次仍失败则**降级为一句安全的最短回应**（按输入是否含情绪选择「情绪回应」或
  「记录确认」），保证违规内容不出现在用户面前。
- 需要判断的那些（是否先接情绪、是否在给建议、是否贴标签）通过把规则写进 AI provider 的指令来约束，
  并由测试对**行为性质**做断言。

### 技术栈与运行形态

- **TypeScript + Node 单一工程**（工程文件在仓库根），领域逻辑与界面层分居 `src/` 下两个顶层目录；
  `src/` 内部的进一步结构由实现时决定。
- **本地 Node server**（只在回环地址监听）+ **Vite 构建的网页**。API key 只存在服务端的环境变量文件里
  （不进 git），浏览器拿不到 key。
- **SQLite 文件库**作为存储，外键 `ON DELETE CASCADE` 承担级联删除。
- **AI provider port 的默认真实实现**：云端 LLM 用 DeepSeek `deepseek-flash`（OpenAI 兼容端点 + JSON 输出）
  负责 `extract` / `judgeLink` / `compose` / `respond`；embedding 在本地 CPU 上用预训练的**多语言**小模型
  （如 `multilingual-e5-small` 这一类，经 transformers.js 在 Node 内运行），完全离线、无需 key。
  模型文件不进 git。
- **可切换**：provider 通过配置选择「云端 OpenAI 兼容端点 / 本地 Ollama」与「本地 / 云端 embedding」四种组合，
  领域逻辑不感知差异。
- **不引入**：任何 agent 记忆框架（mem0 / Letta / Cognee / LangMem）、任何图数据库、任何模型训练或微调。
  借鉴的是它们的模式（阈值汇集、防抖、失效不删除），不是它们的代码。
- **测试运行方式**：单进程、不 spawn 子进程（受限沙箱下 spawn 会 `EPERM`）。优先用 Node 自带的 type stripping
  直接跑测试入口（本机 Node v22.23.2 支持），不引入会 fan out 子进程的测试运行器。

## 测试决策（Testing Decisions）

- **什么算好测试**：只断言**外部行为**。测试从领域核心 interface 发起，断言用户能观察到的事实 ——
  事项有没有被分出来、留档是否保真、追问是否指出出处、回应是否先接情绪、浮现是否遵守冷却与条数上限、
  删除后是否真的不再出现。不断言 SQL 表结构、不断言内部函数调用、不整段断言 prompt 文本。
- **被测 modules**：领域核心（通过它的 interface 端到端测，AI 全部由假 provider 提供确定性）；AI provider port
  的真实实现只做少量**手工冒烟**（能连通、返回结构符合预期），不测它的语义质量。
- **不测**：网页 DOM（三幕由人工过一遍）、SQLite 内部行为、真实 LLM/embedding 的输出质量、成本。
- **假 provider 的形状**：按调用参数返回预置 JSON 的脚本化实现；额外提供「故意违反回应规则」的脚本，
  用于验证**校验 → 重生成一次 → 降级为安全回应**这条路径。
- **必测的关键行为**（覆盖风险最高的几处）：
  1. 一段混杂输入同时产出事项与留档，且留档是原文；
  2. 情绪输入的回应第一句是情绪回应，且不含「为什么」、不超 3 句；
  3. 追溯命中时给出出处，未命中时明确说没找到；
  4. 阈值未到时不出结论；跨过阈值时出结论且带支撑词条；
  5. 冷却期内同一主题不重复浮现；每轮最多一条；
  6. 浮现与答案一律为不确定语气；
  7. 删除预览报出受影响的小结论数量；确认级联删除后追溯不再返回它的内容；
  8. 标「不对」后旧结论仍在链上、新结论与其构成推翻关系。
- **先例**：本仓库现有的唯一测试是 `tools/check-workspace.test.mjs` —— 一个可直接执行、内含断言、以退出码表达的
  单文件测试，用 `node tools/check-workspace.test.mjs` 跑（**不要用 `node --test`**，受限沙箱下会 spawn EPERM）。
  新测试沿用这个形态与运行方式；在出现第二个被测单元之前不引入测试框架。
- **测试数据的先例**：目前没有。领域测试自建**预置数据**（与 demo 第三幕共用同一套预置词条/投递），
  因为第三幕的可演示性本身依赖这套数据。

## 不在范围内（Out of Scope）

- 注册、登录、多用户、账号与数据隔离（纯本地单用户）。
- 移动端（终局目标，本 spec 不涉及）。
- 系统级推送、通知与提醒可靠性保证；冲突检测；完整日历 UI。
- 图数据库、向量数据库、任何 agent 记忆框架的引入。
- 任何模型训练 / 微调；任何置信度校准工作；semantic entropy 多次采样。
- 跨用户数据匹配（「知己」）、域名上线。
- 真实 AI 生成质量的调优（prompt 迭代、模型对比）；demo 只要求链路成立、行为可断言。
- 完全本地推理的**实测**与性能优化（provider 层留好口子，换本地 Ollama 属后续阶段）。

## 补充说明（Further Notes）

- **三幕 demo 的脚本**（沿用 `NEXT.md` 已冻结的边界）：① **丢** —— 丢一段含老师讲的评分标准 + 一句情绪的
  杂乱输入，不选类型、不填时间，自动分出事项与留档；② **问** —— 以「几天后」的视角问「期末怎么算分」，
  准确答出并指出源自哪次投递；③ **浮** —— 再丢一句情绪化输入，浮出一条不确定语气的小结论，
  由**预置的足够词条**支撑。三幕都跑在预置数据上，保证可重复。
- **成本与隐私**：按调研的账本，单用户一年 API 成本约 **$0.2–1.0**；demo 的默认组合是「原文出机器（云端 LLM）+
  embedding 留本地」。这是本项目唯一值得纠结的取舍，已在实现决策里留好切换口。
- **调研结论已吸收**：不训练任何模型；链接用预训练 embedding + 阈值；阈值汇集照抄 Generative Agents 的形状；
  防抖与「失效不删除」两个模式进入实现决策；CPU 吞吐量缺一手数据，因此**不在 spec 里承诺本地延迟指标**，
  上台本地推理前先在自己机器上实测。
- **回应方式的权威来源**：`docs/ytwins/parent-voice-principles.md`。其中末尾「产品作者补充的规则」一节
  （不确定语气、长度上限是工程设定）与书本提炼部分同等生效；本 spec 不复制它的规则文本，只定落地方式。
- **首次配置需要一个人类动作**：申请并填入云端 LLM 的 API key（服务端环境变量文件）。这一步只有人能做，
  必要时用 `/wizard` 生成一份交互脚本，不要把它写进 agent 的实现 ticket。
- **尚未定值的参数**（属调参，不进术语、也不阻塞实现）：阈值数值、灰区边界、防抖窗口、主题重叠比例、
  词条相关度分数口径。它们由可配置常量承载，先给一个能跑通 demo 第三幕的初始值，之后再按真实数据校准。
- **schema 变更预期**：存储首次落地即包含投递/留档、词条、链接、小结论、结论链、事项、浮现记录七类实体；
  后续如引入「答案的版本」，沿用结论链的推翻/继承关系，不为它单开一套机制。
