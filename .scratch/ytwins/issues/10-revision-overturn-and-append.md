# 10: 修订 —— 标「不对」与补一句自己的话

**What to build:** 用户能把某条**小结论**标为「不对」，这次否定在**结论链**上成为一次**推翻**：
原结论保留、不被覆盖或删除，新的判断与它构成推翻关系。用户也能在结论旁边补一句自己的话，
而那句话本身成为一次新的**投递**，进入同一条链路继续参与沉淀。

**Blocked by:** 05（阈值汇集 —— 第一条小结论、画像与结论链）

**Status:** ready-for-human

- [x] 标「不对」之后，被否定的旧结论**仍在结论链上**，可查看。
      → 旧结论一字未改：句子、支撑词条、创建时刻、在链上的位置都还在（`domain.test.ts`
      的「marking a conclusion wrong keeps it…」逐条钉住）。这不是「实现时小心一点」，而是本次唯一的
      写法：标不对只往 `conclusion_` **追加**一行，全程没有一句 UPDATE、没有一次 DELETE。
- [x] 标「不对」之后，链上出现一条与旧结论构成**推翻**关系的新记录，并说明它取代了哪一条。
      → 新记录 `kind: 'correction'`、`relation: 'overturn'`、`supersedes` 指向被否的那条；
      页面在同一行渲染「推翻了「…」」，所以「取代了哪一条」是**读得出来**的，不只是一个 id。
      入口是 `domain.markConclusionWrong(conclusionId)`，返回刚写下的那条记录。
- [x] **结论链只增不改**：任何修订都不覆盖、不物理删除旧结论。
      → 只追加。重复标同一条**只记一次**：第二次返回同一条记录，链不再变长。
- [x] 在结论旁补一句自己的话，那句话作为一次新**投递**落库，并保留原话。
      → `domain.appendToConclusion(conclusionId, body)` 复用 `drop` 的整条路径（`recordDrop`）：
      原话逐字落库、照样拿到一句回应、照样出现在「接住了什么」里。
- [x] 那句补充的话同样被抽出**词条**，并参与后续**沉淀**。
      → 它是投递，所以走同一套抽取 / 链接 / 归并。**「进入同一条链路」是结构保证而不是运气**：
      它带着 `pinned_matter_id`（那次投递就是写在**这条结论**旁边），归并时直接落进那件事，
      不再靠词面重合去猜。下一次沉淀出的小结论 `supersedes` 就是它写的那条（或那条的推翻记录）。
- [x] 没有打分、点赞或批量反馈功能 —— 对**无感**的这条红线做行为断言（界面上不存在这类入口）。
      → 三处断言：① API 侧 `/api/conclusions/<id>/{rate|like|score}` 与 `/api/rate` 全是 **405**，
      且两个真操作**只按路径里的一个 id** 工作 —— 没有任何请求形状能装一个分数或一串 id；
      ② 画布（`/api/conclusions` 的响应）的 key 集合被逐个钉住，里面没有评分字段；
      ③ `main.ts` + `index.html` 里不存在能命名这类入口的词（打分 / 评分 / 点赞 / 星级 / 好评 / 差评 / 五星）。
      页面上与结论有关的入口只有两个：这条不对、补一句自己的话。

## Comments

**2026-09-17 — 实现完成**

### 新增的领域词汇与形状（`src/domain/interface.ts`，最高 seam）

- `ConclusionKind` 第三档 `'correction'`：链上**唯一不是判断**的那种记录 —— 它记的是用户对前一条做的事。
  与 `claim` / `catch` 分开，是因为三者向读者交代的是不同的事（「我是这么看你的」/「我只接到这一步」/
  「这是你对我上一条说的话」）。
- `ConclusionAddition { conclusion, drop }`：一句话写在某条结论旁边，同时**也是一次投递**。
  两半一起报，是因为两半同时为真。
- 新操作两个：`markConclusionWrong(conclusionId)` 与 `appendToConclusion(conclusionId, body)`。
- `ConclusionPolicy` 多两个值：`overturnedOverlapFactor: 0.3`、`overturnedBandDrop: 1`；
  `Conclusion` 多一个字段 `softened`（这一档是被退过的，页面把它当作第四个输入说出来）。
- 存储多两列：`drop_.pinned_matter_id`（可空，带 `ON DELETE SET NULL` 与 `ensureColumn` 迁移）与
  `conclusion_.softened`（`INTEGER NOT NULL DEFAULT 0` —— 有规则读它，所以**带默认值**加，照 08 的教训）。

### 为什么「不对」那条记录由**代码**写，而不是让 provider 写一句新的

这是产品作者在本次开工前定的一句话（两个选项都摆在面前时选了它）。理由是产品自己那条最硬的线：
**它不能说出它没有的判断**。用户刚说的是「你这条看错了」，此时把旧结论交给模型写一版「修正后的说法」，
等于产品借这次否定**再编一条关于用户的看法** —— 那条看法没有任何材料支撑，用户也没说过。
代码写下的那句是**事实**（用户做了这个动作），所以照实陈述、不加不确定语气（`CONTEXT.md` 对
**事实**的要求：给事实加「似乎」同样是不诚实）。

那句话是 `conclusions.ts` 里的 `CORRECTION_LINE`：「你标了这条不对。」它不引旧句子，因为记录本身
已经 `supersedes` 指向它了 —— 同一件事存两遍，只会多一处能对不上的地方。

### 为什么 `kind` 是新的一档，而不是复用 `catch`

`catch` 的定义是「只接住用户最新那句情绪」，`tier: null` 在文档里的含义是「它什么都没断言」。
承接与修正确实都在「没有断言」这一点上相同，但它们对读者的意思完全不同，而且**语义会渗到下游**：
浮现（06）只挑 `claim`，两种都不是；页面对承接渲染「承接」、对修正渲染「修正」、
对修正也不问「为什么这么说」。把修正塞进 `catch` 会让这三处都得再判一次「是哪种 catch」。

因此 `tier` 的文档从「null 就是 catch」改成「**没有断言**的都为空」—— 一个 catch、一个 correction。
`mentions` / `spanDays` / `averageStrength` 三列是 NOT NULL，修正一律填 **0**：修正不读任何数值，
而被否那条的数值仍留在**那条**上（它自己的「为什么这么说」照旧读得到）。改成可空要重建表
（09 的教训：`ALTER TABLE` 去不掉约束），而「不适用」这件事已经由 `kind` 表达了。

### 为什么「标不对」还要走到语料层（本次清单里没写，但 05 派给了 10）

05 的 prototype 决定第 5 条：「标不对要走到语料层：把该结论倚重的词条之间『算同一件事』的程度降下来
（默认 ×0.3），语气档位随之变弱。」05 的 `## Comments` 把这件事明确派给了 10，10 自己的验收清单没列它 ——
开工前问过作者，选择**做**。不做的后果很具体：标了不对之后那件事照旧吸引长得像它的碎片，
过几天再说出同一句，等于**没听见用户说什么**。

落地成两处读同一个事实（`overturnedMatters()`：链上有一条 `correction` 就说明这件事被否了）：

1. `attach` 里量重合时，被否的那件事**打 `overturnedOverlapFactor` 折**。阈值是 0.50、重合上限是 1，
   所以 0.3 折是**决定性的**：被否过的事只能靠用户**自己写在旁边**的那句话再长东西，猜不进去。
   降的是**归类**，不是事实 —— 哪些词一起说过、它们之间的链接强度，一概不动。
2. `settle` 里读档位之后 `softerTier(...)`：被否过的事再说话，档位**退一档**（strong→medium→weak，
   weak 是地板）。用「一档」而不是再乘一个系数，因为档位是有序的三档，没有更细的刻度。
   **退档与数值之间的账要说得清**：三个数值是事实，一个字都不改；退档这件事作为**第四个输入**写在那条
   结论上（`conclusion_.softened`），页面在「为什么这么说」后面补一句「这件事你标过不对，语气退了一档」。
   这一条是 `/code-review` 逼出来的（见下「审查发现并已修的问题」第 1 条）：不然页面上会出现
   「弱档」+「7 个词条 · 跨 17 天」并排 —— 那组数按 `tierOf` 明明是中档，等于页面自己在讲两个故事，
   而「措辞强弱由可解释数值映射」正是这条记录的立身之本。只在**退档真的改变了答案**时才记：本来就落在
   weak 的那条不算被退过。

这个事实**不落库**（不在 `matter_` 上加标记）：它就是那条 correction 行本身，加一个标记等于同一件事
两份记录，而 09 的 `original-only` 会把保留下来的结论**搬到另一个 matter** 上 —— 那时标记必然漂移。
（落库的是**另一件事**：某条结论的档位当时确实被退过 —— 那是写那一刻的事实，事后从链上推会和当时的
选择对不上。见上面第 2 条。）

### 为什么补一句要**钉**在那条结论所在的事上（`pinned_matter_id`）

两件事只有放在一起才成立。**「进入同一条链路」**是 ticket 的字面要求；而上面那条降级是
**决定性的**（0.3 折之后任何靠猜的归并都进不来）。如果补一句只是「一次普通投递」，那么写在一条被否的
结论旁边的这句话，会**跑到另一件事里去**，谈的还不是用户想谈的那件。所以：

- 写在旁边这件事本身就是用户说出的、比任何重合都清楚的一句话 —— 归并时不再重新推断，
  直接把那次投递落进那条结论所在的 matter。
- 这是**倾向**不是事实：matter 可能已经没了（比如被级联删掉），钉住的目标解不出来时，
  这次投递就按普通规则走。所以外键是 `ON DELETE SET NULL`、**不级联**：matter 没了不该带走投递。

### 为什么一次修订独占一条队列（`queueRevision`）

`markConclusionWrong` 往 `lookQueue` 里排队执行。理由与那条队列存在的理由同源：一次 look 可能正在
为某件事写句子（要等模型），而它写下的 `supersedes` 读的是**它开始时**的链。如果修订在这中间落库，
那条句子就会把自己记在用户刚刚否掉的前驱下面。

与 `queueLook` 的区别只在**回给调用方的那个 promise**：look 是后台活，吞掉失败；而这是用户按下去的
一次写入，失败必须以失败的形式回来 —— 若照 `queueLook` 吞掉，写库失败会被报成
「没有这条小结论」，那是在说谎。队列本身仍然不携带拒绝，否则排在后面的全都跟着掉。

### 一个后果，写在这里免得被当成 bug

一条被标不对的结论，其 matter 最新的记录是那条 `correction`，而**浮现只挑 `claim`**
（06 的规矩：每件事只看最新那条）。所以标记之后，这件事在用户自己写进来新东西并重新沉淀之前
**不会再被浮出来**。这是对的：用户刚说这条看错了，产品回头再把它推到用户面前是最糟的回答。

### 界面（第一幕「画像」一节）

每条记录旁挂两个入口，就是全部：

- **「这条不对」**：只在**是判断**（`claim` / `catch`）且尚未被否的记录上出现 —— 产品自己记下的
  「用户做了什么」没有可被否定的内容；已经否过的也不重复给（重复按也只是同一个事实）。
  按下去不带任何理由：那是**反馈表单**的开头，不是这个产品的东西。
  **同一条规矩在领域里也守着**（`markConclusionWrong` 遇到 `correction` 返回 null，什么都不写）——
  页面只是不把按钮画出来，它不是唯一一道闸。
- **「补一句自己的话」**：每条记录都有，包括修正自己 —— 写在自己那句「不对」旁边把自己真正的意思
  补上是再自然不过的一件事。

链上两个方向都读得出来：往后是「承自「…」」（修正则显示「推翻了「…」」），往前是
「后来被「…」接过」（被修正接过的则显示「后来被你标为不对」）。修正那行**没有**「为什么这么说」，
也没有支撑词条 —— 它什么都没读。

### 「一条结论可能被两个东西接替」这件事

`supersededBy` 保持单值，含义收紧为**最新接替它的那一条**。链是顺序的，但修订会在中间开一个岔：
`C1 → C2`（承接）之后再把 `C1` 标不对，于是 `C2` 与那条修正都 `supersedes = C1`。
往前看只显示最新那一条（就是那条修正），往后走仍然完整 —— 每条都记着它从哪来。
没有改成数组：那要动 05 定下的形状与每一处读它的代码，而用户被鼓励去做的是对**最新的**那条表态。

### 审查（`/code-review` 两轴）发现并已修的问题

两轴并行审过（diff 基点 `fe2b653`，即 09 的提交）。**Spec 轴查出两条实质问题，第一条正是本次最容易糊过去
的那种「页面自己讲两个故事」**：

1. **退档之后，页面上「弱档」与它旁边的数值互相打脸（Spec 轴，已修）。** 第一版只把
   `tier` 换成退过一档的那档，三个数值原样存 —— 于是同一条结论显示「弱档 · 7 个词条 · 跨 17 天」，
   而这组数按 `tierOf` 是中档。`conclusions.ts` 自己写着「页面读到的数与句子外的框不能讲两个故事」，
   `CONTEXT.md` 也要求措辞与支撑度一致。**修法不是把数改掉**（那是事实），而是把**退档这件事**变成
   第四个输入：`conclusion_.softened` 随句子一起落库，页面在「为什么这么说」后面点明原因。
   落库而不是从链上现推，因为它是**写那一刻**的事实：之后链被删改，推出来的理由会和当时的选择对不上。
2. **修正自己也能被标「不对」（Spec 轴，已修）。** 第一版把这条规矩只放在页面（不画按钮），领域照收 ——

   现在领域自己挡：`markConclusionWrong` 遇到 `correction` 返回 null（`deleteDrop` 的先例：null 表示
