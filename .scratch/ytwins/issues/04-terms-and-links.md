# 04: 词条与链接 —— 把碎片连起来

**What to build:** 每次投递抽出**词条**，并保留用户自己的说法（是「想学吉他」，不是「音乐兴趣」）。
**词条**之间自动长出**链接**，两类并存：**同一次投递里共同出现**的零模型硬边，以及**语义相近**的
相似度边（预训练 embedding 的余弦相似度 + 阈值，三段式处理：高分直接连、低分不连、**灰区**才调
`judgeLink`，或先漏连）。每条链接带可比的强度与连接理由，对用户可见（或至少可读）。

**Blocked by:** 02（接住的结构 —— 自动分出事项与留档）

**Status:** ready-for-human

- [x] 抽出的**词条**保留用户自己的说法，而不是被改写成上位概念。
      → 词条就是 `ExtractResult.terms` 里的**原字符串**，`trim()` 之后原样落库（`src/domain/core.ts` 的
      `toTerm`、`sqlite-store.ts` 的 `recordExtraction`）。用例断言「报个吉他班」「想去爬山」逐字相等；
      provider 若把「想学吉他」改写成「音乐兴趣」，页面显示的就是那个改写 —— 没有一层在中间「归一化」。
- [x] 同一次投递里共同出现的词条之间长出硬边链接，全程不调用任何模型。
      → `recordSameDropLinks()`（`src/domain/core.ts`）：任意两条说在一起的词条配一条边，
      强度恒为 `SAME_DROP_STRENGTH = 1`、理由为「出现在同一次投递里」，**只写不读**，不经过 provider。
      用例用一个 `embed` 与 `judgeLink` **都挂起**的假 provider：隐藏边照样长出来，
      而且 `provider.embedded` / `provider.judged` 都是空的 —— 一条都没轮到模型。
- [x] 语义相近的链接由词条向量余弦相似度决定，按三段式处理：高分连接、低分不连、灰区调 `judgeLink`。
      → 余弦与分段在 `src/domain/linking.ts`（`cosineSimilarity` / `decideLink`），比较在 `core.ts` 的
      `linkInto()`。三条路径各有用例：1.00 直接连（`provider.judged` 为空）、0.00 直接不连、0.80 落灰区
      **恰好一次** `judgeLink`；判定为否就不连，判定炸了就当作没有答案、也不连。
- [x] 灰区策略（调 `judgeLink` 或暂时漏连）由一个可配置常量承载，便于日后改口径。
      → `LinkPolicy.greyZone: 'judge' | 'skip'`（`DEFAULT_LINK_POLICY` 默认 `'judge'`），
      与两个边界一起折进 `decideLink()` 的返回值 `'link' | 'ask' | 'skip'` —— 三个读法都在
      `linking.ts`，调用方不会自己去拼「哪一段 + 策略说什么」。用例把策略钉成 `'skip'`：同一个 0.80 的对子
      不连，且 `provider.judged` 为空 —— 「不问」是真的不问。
- [x] 每条链接记录可比的强度与「为什么连上」的理由。
      → 两种边共用一把尺：硬边恒为 1（一起说出口是确定的，没有可估的东西），相似边取**它实际拿到的余弦**。
      理由是人话的 `reason`：`出现在同一次投递里` / `语义相近（相似度 0.90）` /
      `语义相近（灰区判定，相似度 0.80）`。用例断言硬边强度 > 相似边强度，且两条理由不同 ——
      否则「可比」只是一句声明。
- [x] 链接的相似度阈值与灰区边界由可配置常量承载，不散落在实现里。
      → 全在 `LinkPolicy`（`connectAbove` / `skipBelow` / `greyZone`），经 `DomainCoreOptions.linkPolicy`
      交给核心，默认 `DEFAULT_LINK_POLICY`（0.85 / 0.7 / `judge`）。用例换一组边界（0.75 / 0.5）后，
      同一个 0.80 的对子**不经过判定**直接连上 —— 证明数值真的在驱动行为，而不是写在实现里的常数。
- [x] 假 provider 返回确定性向量与确定性 `judgeLink` 判定，因此链接结果在测试里完全可断言。
      → `embedByText`（一文一向量，按 `request.texts` 顺序拼回批次）与 `judgeLinkByPair` /
      `judgeLinkFallback`（`{ kind: 'verdict', related }`），并记录 `embedded` / `judged` 供断言。
      配对键用 `pairKey()`，所以用例不必知道核心把哪一端当 `from`（有一条就用反向书写来钉这一点）。
      未脚本化的编码或判定**直接失败**，不发明向量、也不发明结论 —— 沿用 `composeAnswer` 的规矩。

## Comments

### 2026-09-15 — 两轴 `/code-review` 之后的修订

两轴都找出了真问题，全部已改。

**Spec 轴。**

1. **页面看不到这一张自己的产物。** 原来 `loadLinks()` 紧跟在 `settleDrop()` 之后调一次，而 `settleDrop()`
   一读到 `extracted` 就返回 —— 那时 `linkInto()`（编码 + 判定）还在飞，所以只有硬边画出来了，相似边要刷新
   才出现。改成 `settleLinks()`：读取落地后再对有界的几轮（`LINK_GRACE_POLLS = 4`，约 1 秒）反复读一次
   链接列表，画到的每条都是真的，超出宽限的那些下次加载出现。**没有**做成「落库那一刻保证」——
   相似边本来就要等一次 embedding，那是它的本质。
2. **`package.json` 的 `test:e2e` 被顺手改掉。** 原来只跑 02 的脚本，我一度改成 02 → 03 → 04 串跑。
   这一张没要求改项目的默认入口，已回滚到原样；三个脚本各自按 `tools/README.md` 里的路径跑。
3. **硬边规则曾经住在存储适配器里。** 第一版让 `sqlite-store.ts` 生成硬边，于是它 import 了
   `SAME_DROP_STRENGTH` / `SAME_DROP_REASON` —— 存储层拿着产品文案和沉淀规则，与 spec 的
   「沉淀在领域核心、存储只承载」相反。现在硬边由核心的 `recordSameDropLinks()` 写，存储只提供
   `recordLinks()`（一对其一行、后写的替换先写的，**选哪一条是核心的事**）。代价是硬边与词条不再同一个
   事务：写失败时少的是链接，不是用户说过的话，这个量级上可接受，已写进 `storage.ts` 的 port 文档。

**Standards 轴。**

4. **「灰区怎么办」一度分居两个模块。** `linking.ts` 声称三个决定都在它这里，但 `greyZone === 'skip'`
   却写在 `core.ts`。现在折进 `decideLink()`：返回 `'link' | 'ask' | 'skip'`，灰色带与策略不再由调用方拼。
   `bandFor()` 这个只报「哪一段」的中间层随之删掉（它本来就会诱使调用方重新实现另一半）。
5. **一对词条的两种写法拼了三遍。** 核心的 `pairKey`、存储的 `orderedPair`、假 provider 的
   `${from}\u0000${to}` 各写一份，改成 `linking.ts` 一处导出、三处引用；假 provider 的「正反各查一次」
   也随之简化成一次查表。
6. **`LINK_KINDS` 是第四份词表。** 存储层自己列了一遍 `'same-drop' | 'similar'`，改成
   `interface.ts` 导出的 `LINK_KINDS`（与既有的 `INPUT_TYPES` 同一个做法：类型 + 运行期清单）。
7. **测试文件里有一个写坏之后就没用过的常量** `HILL_TERMS`，已删；`NewLink` 的字段补了文档注释；
   `recordExtraction` 里那句讲词条的注释原来压在删除语句上方，已挪到位。

**顺带补的三条用例**（都先证明旧代码会挂）。硬边**优先于**先到的相似边（原来先到先得，与 ticket 里
「硬边优先」的说法不符）；两个**向量都缺失**的旧词条在它们一起被编码的那一轮要互相比一次
（原来只比较「今天说的 × 其余的」，这一对会永远悬着）；**两个模型的向量不比** ——
`cosineSimilarity` 原来按 `Math.min(a.length, b.length)` 截断，于是 3 维与 2 维的向量会在公共前缀上
比出一个 1.00，规范允许换 embedding 实现，这条就会把无意义的数变成链接。现在长度不同或方向为零一律
返回 `null`（**不可比**，不是「不像」），由核心跳过。

### 2026-09-15 — 实现完成

**这一张做了什么。** 投递除了分出**事项**与**留档**，还抽出**词条**；词条之间有两个来源的**链接**，
两种都带强度与理由，并且都真的可读（页面第一幕列出每条词条与每条链接）。三件事分得很清楚：

1. **抽取**（provider 的 `extract` 多返回一个 `terms`）→ 写进 `term_` 表，按**原文**去重。
2. **硬边**（零模型）→ 核心在词条落库后立刻写，含义是「同一次投递里一起出现」。
3. **相似边**（余弦 + 三段式）→ 在后台独立跑；向量是 `term_.vector`，**不出领域**。

**去重按字面，不按模型。** 「想去学吉他」再说一次是**同一个词条**（`term_.text` 唯一），
「学吉他」是另一个 —— 后者靠相似边连上。理由：让模型去判「这两个说法是不是同一个概念」就是把词条
变成模型的措辞，而这一张的全部意义是保住用户自己的话；而字面去重让「说过三次」真的能累加，
这正是 05 的**阈值**要数的那种东西。`term_in_drop_` 单独记「哪次投递说了它」，
所以重复提起只增加一次提及，不会把词条搬走，也不会伪造一个新词条。

**几个不显然的决定。**

1. **没有别人的时候，一条向量都不算。** `linkInto()` 先看「除了这次说的，还有没有别的词条」，
   没有就直接返回 —— 因此**第一次丢东西不产生任何 embedding 调用**，而词条会在它第一次有对手时被编码。
   用例用一个 `embed` 挂起的 provider 把这条钉住（`provider.embedded` 为空）。代价是：一次投递可能同时
   编码「今天说的」和「以前说过但还没编码的」。
2. **每一对词条，在它两端都有向量的那一轮被比一次 —— 以「后到的那一端」为准。** 所以比较循环是从
   **这一轮刚编码出来的词条**出发，去比所有已经有向量的词条，而不只是「今天说的 × 其余的」：
   两个都因为 provider 挂过而没编码的旧词条，在它们一起被编码的那一轮就要互相比一次，否则这一对会一直
   悬着。这也是「一对只比一次」真正成立的形式。
3. **一次编码是全有或全无，而且向量先落库。** provider 少给一条、给歪一条，这一轮的链接就没了 ——
   但词条是**先**存好的，所以代价只是「少几条边」，不会丢用户的东西。把缺的那几条猜出来才是更坏的选择。
4. **向量不可比时返回 `null`，不返回 0。** 维度不同（换过 embedding 实现）或方向为零（provider 说没得比），
   都不是「不像」而是「没比过」，`cosineSimilarity()` 因此不返回数字，由核心跳过。截断到公共前缀会
   把两个模型各自的数拼成一个看似 1.00 的相似度，并把那条假边写成链接。
5. **一对词条只有一条链接，硬边优先。** 同一对既同投递又语义相近时，后写的那条覆盖先写的，而核心保证
   「硬边会覆盖相似边、相似边不会覆盖硬边」。05 要数「有多少词条连上来」，同一对算两次会把门槛悄悄
   降低。`link_` 的 `UNIQUE (a_term_id, b_term_id)` + 一对一种写法（`orderedPair()`）是执行者，
   **选哪一条是核心的事**，存储只负责「一对其一行」。
6. **灰区判定返回布尔，不是分数。** 这一问的全部意义是裁决一个**已经量出来的**区间；
   再给一个不同尺度的数，只会招来把两个数放在一起比。理由文字里写清是「灰区判定」，
   强度仍是那条余弦 —— 两者不能各说各话。
7. **向量不上 interface。** `Term` 只有 `id/text/dropId/firstSeenAt`，用例显式断言 key 集合，
   与 02 里「输入类型不出现在页面上」同一个做法。余弦不是置信度（调研 §6.1），
   把它摆在页面上会让人以为那是概率。

**页面。** 第一幕每条投递下面多一行**词条**（小圆片，用户自己的话），下面多一节**连起来的词条**：
`「期末怎么算分」 — 「下周三交提纲」` + 理由 + 强度。链接不长在某个投递下面，因为它不属于任何一次投递 ——
它是一次次投递加起来的结果，这也是它必须有自己一节的原因。`/api/links` 是它自己的端点。
投递之后链接列表会给相似边留一个有界的宽限期（`LINK_GRACE_POLLS = 4`，约 1 秒），
因为那半边要等一次 embedding；宽限之后画到的每条都是真的，剩下的下次加载出现。

**预置数据。** `demo-provider.ts` 给 demo 片段加了四个词条（含「好烦」——情绪也是词条，
05 的阈值要数的就是它连上多少东西），于是第一幕真长出 6 条硬边。**没有脚本化 embedding**：
这四条都出自同一次投递，语义那一半此刻没有对手可比；等第二次投递进来才有，
而这正是 05 / 06 的材料，向量该在那里加。

**测试与验证。** 领域 **80/80**（新增 19 条，全部走领域 interface + 假 provider）；
新增 `tools/e2e-ticket-04.mjs` **5/5**（真 HTTP：词条按原话过线、三条硬边带理由、向量不外泄、
跨投递的灰区相似边被判定并连上、重启后仍在）；`e2e-ticket-02` 7/7、`e2e-ticket-03` 6/6 仍全绿；
`tsc --noEmit` 全绿、`vite build` 成功、`check-workspace` clean。真实服务器手工过了一遍第一幕：
丢 demo 片段 → 四个词条 + 六条「同一次投递里一起出现」。

**为下一张留的路。** 05 要的「阈值是数量门槛」现在能数了：词条的身份稳定（字面去重）、
链接有一条算一条（一对只有一条边）、每条边带可比的强度。三个参数（阈值数值、防抖窗口、
相关度分数口径）与 06 的语气映射仍按 NEXT.md 的安排先走一次 prototype。
