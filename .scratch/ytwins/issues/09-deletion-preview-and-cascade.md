# 09: 删除 —— 先告知，再级联

**What to build:** 删除一次**投递**时，系统先明确告知「有 N 条**小结论**是从它来的」，由用户决定是一起
删掉还是只删原文；用户确认后执行删除，且删除一旦发生，它的正文不再出现在任何**追溯**结果或**结论**里 ——
「删掉」是真的删掉，不留孤儿行。

**Blocked by:** 05（阈值汇集 —— 第一条小结论、画像与结论链）、07（追溯 —— 问一件旧事，答得准并指出出处）

**Status:** ready-for-human

- [x] 删除前先返回预览：受这次投递影响的**小结论**数量（例如「有 N 条小结论是从它来的」）。
      → `domain.previewDeletion(dropId)`（`src/domain/interface.ts`）返回 `DeletionPreview`：
      **受影响的小结论原话**（`conclusions`，`ConclusionRef[]`）加上**只有它说过的词条**（`terms`）。
      数量就是这个数组的长度，页面照着说「有 N 条小结论是从它来的：」并**把原话列出来** ——
      只报一个数字是让用户去信一个统计，把句子摆出来才是让他认出自己要放弃什么。
      它**什么都不改**：问两次得到同样的答案，看完不动手就等于没发生。
- [x] 在任何删除真正发生之前，用户必须做出一次明确选择；不存在静默或默认删除。
      → `domain.deleteDrop(dropId, mode)` 的 `mode` 是**必填**的，取值 `'cascade' | 'original-only' | 'keep'`。
      `'keep'` 是三个答案之一且**不删任何东西**（返回 `null`）—— 看完预览决定不删，就是一个决定。
      API 上同理：`POST /api/delete` 不带 `mode` 返回 **400**，模式不认识也 400（不会退回默认值）。
      所以「静默删除」在**调用形状上**就不可达，不是靠约定。
- [x] 选择「一起删」时，受影响的**小结论**被级联删除，不留孤儿行。
      → 见下「为什么小结论是显式删的，不是靠外键级联」。级联从 `conclusion_` 往下带走 `surfacing_`
      （浮现记录），`supersedes` 用 `ON DELETE SET NULL` 修链 —— 指向它的那条链会退回「开链」，
      而不是指着一条读不到的结论。
- [x] 选择「只删原文」时，投递与留档被删除，而衍生出的小结论按既定口径保留或标记失效（实现时二选一并写清理由），且不会崩溃或留下悬空引用。
      → **选「保留」，不选「标记失效」**，理由见下「为什么是保留而不是标记失效」。
      实现上分两步：先把用户要留的小结论**搬到一个删完还在的 matter 上**（`carryOver`），再删原文，
      最后把已经消失的词条从这些结论的 `support` 里剪掉（`pruneSupport`）——
      **句子一个字不改**，改的只是它引用的证据。所以不留悬空引用：支撑里的每个词条都还在。
- [x] 级联删除之后，**追溯**不再返回该投递的任何内容。
      → 追溯（07）挑记录靠的是在**留档原文**里找子串，原文删了就没有可命中的东西 ——
      这是结构上的保证，不是加了一条过滤：删掉的那条不会「被排除」，它是**不存在**了。
      `tools/e2e-ticket-09.mjs` 钉住了「删前答得出、删后 `not-found`」这对断言。
- [x] 级联删除之后，**画像**与**结论链**里不再残留它的痕迹。
      → 画像就是小结论的集合（`listConclusions()`），结论链是它们之间的承接关系；
      结论删了，两者同时为空。e2e 把**整个 `/api/conclusions` 响应**序列化后断言正文与支撑词条都搜不到。
- [x] 级联删除之后，指向它的**词条**与**链接**一同清除，不留孤儿行。
      → 改成「**只有这次投递说过的**词条随之删除，被别的投递也说过的不删」。见下「共享词条怎么办」——
      这是本次实现里唯一一处与字面要求有出入的地方，理由写在那一节。

### 为什么小结论是显式删的，不是靠外键级联

`conclusion_` 挂在 **matter** 上（`matter_id ... ON DELETE CASCADE`），而 matter 挂在**词条**上。
删一次投递只会在「这次投递是该 matter 的最后一个成员」时才波及 matter —— 一个用户反复提起的
matter 会**活下来**，于是「一起删」会悄悄退化成「什么都没删」：比两个选项都糟。
所以 `cascade` 是**显式**删小结论的；外键只负责把 `surfacing_`（浮现记录）和链上的悬空引用一起收干净。

### 为什么是保留而不是标记失效

ticket 让二选一。选**保留**的理由：**画像是一份「当时是怎么想的」的历史**，不是一份会跟着数据回填的
当前状态。把旧结论改写成「这条已作废」，是产品**修改自己的过去**让它更好看；而用户选「只删原文」时
说的是「别记得我说过这句」，不是「你当时想错了」。两个选项都不给安全感上的便宜，那就选不动句子的那个。

代价说清楚：`original-only` 之后，画像里会留下一条**用户已经无法逐字核对**的小结论 —— 原文没了。
这是这个选项本身的含义，不是实现的疏忽；要连结论一起走，那个选项叫 `cascade`。

### 共享词条怎么办（与字面要求有出入的一处）

ticket 写的是「指向它的**词条**与**链接**一同清除」。字面执行会伤及**别的投递**：
`term_` 一个写法一行（04 定的规矩），所以「好烦」在周一、周二、周三说过就是**同一个** term，
三条投递都 mention 它。删周一那次要是把 term 带走，周二、周三那两次就**凭空少了一个它说过的词**——
那是在悄悄改写用户没删的内容。

所以口径是：**这次投递是最后一个说它的，才删**（`orphanedTerms()`，数的是「还有谁在说」，
不是「它最早从哪来」）。留下的那类，`link_` 不删，因为它指向的词条都还在；删掉的那类，
`link_` 随词条级联清掉。留在 matter 的 `support` 与 conclusion 的 `support` 里、但**行已经不在**的词条
一律剪掉，所以两边都不留悬空引用。

### 踩到的坑：`term_.origin_drop_id` 的级联是错的（本次唯一的 schema 改动）

第一版跑出来，「好烦」在级联删之后**消失了** —— 周二、周三那两条投递凭空少了一个词。

根因不在删除代码，在 02 留下的 schema：`term_.origin_drop_id REFERENCES drop_(id) ON DELETE CASCADE`。
当时写它的理由是「nothing exists without a source」，读起来无害，实际是错的 ——
**级联只有在「这条引用是唯一撑着这行东西」时才对**。一个写法一行的 term，被多条投递 mention，
`origin_drop_id` 只是**其中一个**提及者，把它当父行就等于说「第一次说它的那次投递没了，这个词就不算说过」。
于是本次把它改成**不带外键**（新库），并加了一次**重建表**的迁移给旧库（`dropTermOriginCascade()`，
`ALTER TABLE` 删不掉外键，只能重建表格；`PRAGMA foreign_keys` 在事务里关不掉，所以重建期间关、结束再开）。
删投递时由代码把存活词条的 `origin_drop_id` 置 NULL。

这条教训比本次的实现更值钱，已写进 `sqlite-store.ts` 的 schema 注释。`domain.test.ts` 里补了一条
**手工造 01–08 旧库、再删一次投递**的检查，专门钉住「迁移之后不能再丢词」。

### 删除后剩下的话又跨阈值，会不会重新浮一条？

**会，而且这是对的。** matter 没随投递消失（还有两条成员），它剩下的词条仍然支撑一个判断，
那就该重新说出来 —— 而且新那条的支撑里**不会有删掉的成分**（`good` 的支撑已剪过）。
反过来「保持沉默」才是错的：那等于把用户**没删**的材料也一起打折了。
`tools/e2e-ticket-09.mjs` 里那条 check 因此不叫「删了就不会再浮」，而叫
「级联之后说的话只建立剩下的东西之上」—— 断言的是**它站在什么上面**，不是它闭不闭嘴。
