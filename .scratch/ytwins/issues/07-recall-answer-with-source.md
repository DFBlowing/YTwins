# 07: 追溯 —— 问一件旧事，答得准并指出出处

**What to build:** 对**留档**提问（例如「期末怎么算分」），得到准确的回答，并看到这条答案来自哪一次
**投递**，可以核对到保真原文。召回不足时它**直说没找到**，而不是编一个听起来合理的答案。
为了让这一步早就能独立验证，用户可以手工指定「现在是几天后」的时间基准，不必真的等。

**Blocked by:** 01（工程骨架与第一次「丢」打通全链路）

**Status:** ready-for-human

**已认领并完成**（2026-09-15，在 02 提交之后重做）：RED → GREEN 走完，14 条 recall check 全绿，
同一份工作里把第二幕（问）填实。过程记录见文件末尾的 `## Comments`。

- [x] 提问命中**留档**时给出准确回答，并指出它源自哪一次**投递**。
- [x] 召回不足时返回明确的「没找到」，不生成听起来合理的答案。
- [x] 答案可追溯到保真原文（与用户当时输入逐字相同的那份内容）。
- [x] 问题的解析与答案的生成都经由 **AI provider port**，测试使用假 provider 因此结果确定。
- [x] 用户可手工指定时间基准（用于 demo 里「几天后」的视角），该基准影响答案措辞与时间引用，但不改变召回结果。

**已改（Spec 轴）。**

### 2026-09-15 —— 实现记录

**做了什么。** 领域核心新增 `recall(question, options?)`，返回一个判别联合 —— 要么
`{kind:'answered', answer, source}`，要么 `{kind:'not-found'}`。没有「空字符串答案」这种形态，
调用方不可能把两者混淆。

**切法**（早先已与用户确认）：AI provider port 加两端 —— `parseQuestion`（问题 → 线索）与
`composeAnswer`（命中的留档 + 时间基准 → 答案句）；**两者之间的挑选是领域核心里的普通代码**：
线索去空白后，逐个在留档原文里找子串，命中即算。所以「没找到」是关于数据的事实，不是模型的意见，
同一个问题永远召回同一批记录。

**几条不显然的决定。**

1. **空线索被先丢掉**。模型返回 `['']` 或纯空白时，因为任何字符串都包含空串，会把每一条留档都判成命中 ——
   正好把「没有可找的东西」变成「什么都能回答」。去掉空白后为空即 `not-found`。
2. **provider 的任何失败都落到同一个 `not-found`**：没有 provider、`parseQuestion` 抛错、
   `composeAnswer` 抛错，三条路径同归。召回对用户只有一个失败面，而这个面是诚实的。
3. **没有证据就不调 composer**。测试断言了这一点（`composed === 0`）——「没找到」由代码说，
   不由模型去措辞一个它无法核实的缺席。
4. **出处取最早命中那一条**。composer 可能用上多条，但指不出一条原文的答案不可核对，而可核对正是这个功能的意义。
5. **时间基准只进 composer**，不进挑选。因此它只改措辞与时间引用，改不了召回结果。
6. **`/api/recall` 的「没找到」是 200 不是 404**：它是关于用户数据的真实回答，不是错误状态。

**为什么服务器里接了 provider。** 01–11 按 spec 全用假 provider（真实实现在 12）。但服务器原先一个都没有，
那样第二幕只会永远「没找到」。所以新增 `src/web/demo-provider.ts`：把三幕的**预置数据**收在一处
（spec 明确允许 demo 跑在预置数据上），由 server 用作 12 之前的替身。它不持有任何 key。

**验证**：`tsc --noEmit` 干净；领域测试 37/37（原 23 + 14 条 recall）；检查器与其测试通过；
`vite build` 成功（需一次不设限执行，见 `NEXT.md` 的沙箱说明）；起真实服务器端到端跑过 ——
丢进 demo 那段话 → 抽出事项 → 问「期末怎么算分」→ 得到答案且出处是原文逐字，问不相干的事 → 明确「没找到」。
