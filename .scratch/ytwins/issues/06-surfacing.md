# 06: 浮现 —— 情绪投递时的那一条

**What to build:** 当用户**情绪投递**时（而不是任何时候），系统尝试**浮现**一条**小结论**：
默认不主动推送，每轮最多一条，同一主题 **7 天内只浮一次**，且措辞一律是不确定语气（「你似乎…」「你最近…」）。
措辞的强弱由**可解释的数值**决定（支撑词条数量、平均链接强度、时间跨度），而不是让模型当场「感觉」
一个语气 —— 这样日后能回答「你当时为什么这么说」。支撑不足时宁可不浮，或明说「我不太确定」。

**Blocked by:** 05（阈值汇集 —— 第一条小结论、画像与结论链）

**Status:** ready-for-human

- [x] 只有**情绪投递**或用户主动询问才尝试浮现；其余投递不触发。
- [x] 每轮最多浮出一条；零条是正常结果（冷却中、或支撑不足），不是错误。
- [x] 同一主题 **7 天内不重复浮现**。
- [x] **主题**的工程定义是「支撑该结论的词条集合的语义重叠」，重叠超过一个由可配置常量承载的内部比例即视为同一主题。
- [x] 浮现内容一律为不确定语气，措辞强弱由支撑词条数量、平均链接强度、时间跨度这些可解释数值映射得出，不由模型自由选择语气。
  **不确定语气是一种措辞形式，不是某个固定句式** ——「你似乎…」只是例子之一，同一档可以有「看起来…」
  「听起来…」「会不会是…」等多种说法。校验要判「有没有被说成断言」，不要按词表要求出现某个词。
- [x] 不确定语气只作用于**判断**（**答案**与**浮现**），不改写普通**回应**。
  判据见 `CONTEXT.md` 的「判断」与「事实」：约束的是**判断**，不是**事实** ——
  在用户之外已经确定的内容照实陈述，加「似乎」同样是不诚实。**追溯**答的正是事实，所以不在本条约束内
  （07 已完成，其答案是陈述句）；不要把它也一并改成不确定语气。
- [x] 支撑不足时不浮现，或明确说「我不太确定」，不靠断言烧掉信任。
- [x] 每次浮现留下记录，使冷却判定在重启后依然成立。

## Comments

**2026-09-15 · 从 05 之前的 prototype 带过来的输入（不算本 ticket 的范围扩张，是实现时的约束）**

1. **三个时刻别混**：每条投递的**回应**是即时的（ticket 03 已做）；**判定**是防抖的、用户看不见（ticket 05）；
   **浮现**是用户看得见的那一次，只发生在本 ticket 规定的时机。所以防抖窗口不会让用户多等 ——
   但**用户主动询问时，必须当场先判一次再回答**（否则最后几句话还没算进去，回答会显得过期）。
2. **神秘感与随机性落在这里，不落在 05**。作者要的「不让用户捉摸到内部逻辑」在判定那一层是无效的
   （判定用户看不见），place 它在这里：到点了也可以掷一次骰子决定这次浮不浮、从够格的候选里挑哪一条、
   同一档换哪种说法。**用户主动问的时候必答，不掷骰子。** 05 那边的「判定时机交替」照旧，但它不承担神秘感。
3. **承接与措辞档位的分工**（`CONTEXT.md` 已有「承接」词条）：弱/中/强三档只作用于**判断**；
   **承接**是支撑不足（默认撑它的词条 < 3 个）时的替代，它不作判断，所以**不加**不确定词
   （「那样真好。」而不是「你似乎松了口气」）—— 给承接加「似乎」是另一种不诚实。
4. **档位门槛的定值**（与 05 共享，已判定）：中档「词条 ≥ 3 且 跨度 ≥ 3 天」；
   强档「词条 ≥ 6 且 跨度 ≥ 14 天 且 平均连接强度 ≥ 0.80」。**句子一律跟这件事里最新那句情绪走** ——
   作者实测过：先说「好烦」、后说「松了口气」，旧写法答「心里一直不太顺」是错的。
5. **同一主题的重叠口径**：用「字面重叠 ÷ 较小的一侧」@ 0.50，并**给共享词按稀有度加权**
   （`权重 = 1 / 该词横跨的事数`）。注意 05 的实测：比例这个旋钮**分不开**「误判」与「真事」
   （两者重叠值相同），所以本 ticket 判「同一主题」时不要指望调比例，要用加权口径。

**2026-09-16 · 实现时的三个拍板与一处推翻（都是产品作者定的）**

1. **第三幕靠「再丢同一句」凑够 3 次**。阈值数的是「同一件事被提起几次」（05 定的 3 次），而三幕是
   「第一幕丢 1 次 + 第三幕再丢 1 次」= 2 次，跨不过阈值。作者选：第三幕继续丢**同一份预置情绪素材**，
   丢到第 3 次时浮现。**不动任何常量、不改阈值**；页面提供「再丢一次第一句」（取库里第一句原文，避免页面里
   再存一份预置数据）。
2. **骰子默认必浮**（`surfaceChance: 1`）。作者选：到点了默认浮，骰子只用于「从够格的候选里挑哪条」与
   「同一档换哪种说法」。理由是 demo 不能靠运气（spec 65）；把机会值调低是日后从真实使用里决定的旋钮，
   位置已经留在 `SurfacingPolicy` 里。
3. **两个时机都当场判一次**（包含情绪投递，不只是主动询问）。作者选：情绪投递时也 `settle` 一次，
   否则第三幕能不能浮出来会取决于 05 那套「判定时机交替」当前落在哪一回合。代价是防抖窗口在情绪投递上
   不再拦住判定 —— 但能被说出来的只有**已经跨过阈值**的事，所以代价是「早一点说」，不是「乱说」。
4. **推翻：不用词表判「有没有被说成断言」。** 第一版实现照票面字面做了
   `UNCERTAIN_FORMS` 词表（判句子里有没有「似乎/好像/看起来…」），`/code-review` 的 Standards 轴抓到
   它直接违反 `docs/ytwins/parent-voice-principles.md`「校验要判的是「这句话有没有被说成断言」，
   **不是「有没有出现某个词」**——按词表匹配会把多样的、更自然的说法误杀」（文档自举的「有一点像」就被误杀）。
   现在的做法是**把不确定语气写进去，而不是去认它**：句子的语气档位（弱/中/强）由 05 的数值映射给出，
   浮现时由代码在该档自己的若干**开头**（`SURFACING_OPENINGS`）里挑一个加在句子前面 ——
   于是每条浮现**结构上**必带不确定语气，不再有「按词表要求出现某个词」这回事；同一档的多种说法也正好落在
   这里（票面第 5 条要的「同一档可以有多种说法」，05 的 review 也指定它属于 06 的外层）。
   代价与附带的一处数据改动：**结论自己要留着模型写的那句原话**（`conclusion_.claim`），
   否则浮现时只能从「已加框的句子」里把框剥回来 —— 那等于把今天的 `frameFor` 当成历史事实。
   结论在画像里的显示**不变**（仍是原样的框），改变的只是「浮现那句话」这一层。

**代码落点**

- `src/domain/surfacing.ts`：`SurfacingPolicy`（冷却 7 天、主题重叠比例、`surfaceChance`）、
  同主题口径 `isSameTopic`（复用 05 的 `overlapOf` + 稀有度加权）、档位开头 `SURFACING_OPENINGS`
  与 `surfacingLine`。
- `src/domain/core.ts`：`requestSurfacing`（两个时机 → 走同一条 `lookQueue` 当场 `settle` → 冷却过滤 →
  骰子 → 留档）、`isAMoment`、`readySurfacings`、`spreadWeigher`（`attach` 与浮现共用同一口径）。
- `src/domain/storage.ts` + `sqlite-store.ts`：`surfacing_`（出具的记录，冷却的根据）、
  `conclusion_.claim`（模型写的那句原话）。
- `src/web/`：`POST /api/surface`、第三幕填实（再丢一句 / 重复第一句 / 主动询问 / 浮出的一条 + 数值 +
  支撑词条）、第一幕投递后内联显示浮出的一句。

**实现时定下的几处判断（票面没写、异步世界必须有）**

1. **「用户主动询问」与「情绪投递」在界面上是同一个动作**。票面把「情绪投递时的浮现」记为 06、
   「主动询问拿到一次观察（答案）」记为 11，但 11 显式写着与浮现**共用同一套冷却与条数上限**、
   「不会在同一轮里各出一条」—— 两者是**同一个 moment**。所以 06 的 interface 一次只开一个操作：
   `requestSurfacing(options?)`，带 `dropId` 就是投递触发的那个时机，不带就是用户主动问。
   11 要做的是在这个操作上加「由**多条**小结论汇集」的那层（票面第 1 条），不是另开一个通道。
2. **零条结果是带原因的**（`not-a-moment` / `nothing-to-say` / `cooldown` / `held-back`）。
   页面**一律不显示**这些原因（浮现不推送），它们服务于领域测试与 e2e；页面只在「压根没问成」时另说一句，
   因为「没能问」与「问了但没什么可说」是关于用户数据的两种不同事实。
3. **承接永远不浮**：候选只取 `kind === 'claim'` 且带着档位与原话的那些。承接不作判断，所以没有可陈述的
   观察 —— 这是「承接不加不确定词」的**结构**保证，不是字符串校验。
4. **冷却从「出示的那一刻」算**，不是从结论汇集的时刻算；记录落库，重启后仍然成立（e2e 跨进程验过）。
5. **试几次是为了等素材落地**：投递后台是「抽取 → 词条 → 归入一件事」几段各自跑的，页面在抽取完成那一刻
   问的时候，归入可能还没落地。没浮出东西时页面最多再问 3 次（约 0.75 秒），而**一旦浮出过**，再问就是
   `cooldown` —— 同一句不可能出现两次。
6. **第三幕的「再丢一次第一句」取库里第一句原文**，不在页面里存第二份预置数据：预置数据只有
   `src/web/demo-provider.ts` 一处，页面抄一份必然会漂。

**`/code-review` 两轴结论与按结论做的处理**

Standards 轴两条硬违规，都已改：

- **词表判断言**（见上第 4 条，改成「语气由代码给出」）。
- **`tools/README.md` 没有为新的 e2e 脚本占一行**（`docs/agents/workspace-layout.md` §`tools/` 的明文要求），
  已补。

Standards 轴的判断项：`main.ts` 本地镜像 payload 结构 —— **不改**（该文件既有习惯就是这样，且页面类型
不依赖 `src/domain` 的类型导入）；`ReadySurfacings` 的非空元组 —— **保留**（它让「零条」无法被表示成一条
空列表，这正是「每轮最多一条、零条是正常结果」的类型表达）；`spreadWeigher` 每次浮现全表读 —— **不改**
（单用户本地库，量级与 `listLinks` / `listConclusions` 同阶，是可读性换来的）。

Spec 轴五条，逐条处理：

- **e2e 已失效**（档位换说法后脚本只认第一种）—— 属实，已修：脚本把 `random` 钉在第一面（脚本管的是线，
  不是措辞），并加注说明「真实服务器跑的是 `Math.random`」。
- **「情绪投递」的判据比 spec 窄** —— 属实且有实质影响（「心里堵得慌」这类没有线索词的情绪不会被当成时机）。
  已改为**两个读法取其一**：代码线索（`readSituation`）**或**模型给的**输入类型**为情绪。
  理由是两种误判代价不对称：漏掉一个时机等于用户该看到的那条永远看不到，而多重试一次最多是把已经跨过阈值、
  且已过冷却的东西拿出来 —— 那条本来就是给他的。并补了一条测试钉住这条边界（同一句话分别被判为
  `emotion` 与 `decision`，只有前者是时机）。
- **`SURFACE_GRACE_POLLS` 让一次投递最多重判 6 次，绕开防抖** —— 部分属实：重试确实会重复当场判定
  （这正是「情绪投递也当场判一次」的代价，拍板时已接受），但 6 次是把代价放大了，已降为 3 次（约 0.75 秒），
  并在注释里写明这个等待为什么有界。
- **第一幕加内联浮现行，而 spec 的「浮」在第三幕** —— **不改**，理由：浮现是「在用户看得见的时刻呈现」，
  它发生在**情绪投递的那一刻**，而第一幕就是投递的地方；只在第三幕显示等于要求用户自己走过去看，
  那反而违背「那一句就该在他投递之后出现」。第三幕是**演示**这一幕的地方（可重复、可主动询问），
  不是它唯一的出口。
- **「校验有没有被说成断言」现在无人执行** —— 属实，已在上面第 4 条写明：改成结构性给出，而不是回头去认。
