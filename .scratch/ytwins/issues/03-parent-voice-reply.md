# 03: 回应方式 —— 情绪优先与机械规则校验

**What to build:** 每次投递都能拿到一句简短的**回应**。输入里含情绪时，回应的第一句是情绪回应，而不是
信息、结论、建议或提问。那些可以机械判定的规则由**代码校验**，不指望模型自觉：校验失败时**重生成一次**，
第二次仍失败则**降级为一句安全的最短回应**（按输入是否含情绪选择「情绪回应」或「记录确认」），
保证违规内容不出现在用户面前。

**Blocked by:** 02（接住的结构 —— 自动分出事项与留档）

**Status:** ready-for-human

- [x] 含情绪的投递，其**回应**的第一句是情绪回应（替用户把感受说出来），不是信息、结论、建议或提问。
      → 能机械判的那半是硬的：含情绪时**首句不得是问句**，违反即拒（`question-when-emotion-first`，
      `src/domain/parent-voice.ts`）。「是不是只陈述了信息」读不出来，交给指令第 2 条；兜底是固定的情绪线
      「听着今天不太好受。」——provider 答不出时，情绪投递拿到的就是它。
- [x] 不含情绪的投递不硬凑情绪回应。
      → `readSituation()` 按词表判定；不含情绪时降级线是「接住了。」，指令第 3 条明写「没有情绪就平淡确认」。
- [x] 代码校验以下机械规则：不超过 3 句、约 60 字；不以「为什么」起问；单轮最多一个问句；无禁用词表；
      无亲昵称呼；无「但是／不过／至少」这类转折收尾。
      → `checkReply()` 返回**违反的规则名**而不是布尔：`too-many-sentences`、`too-long`（不计空白）、
      `why-question`、`too-many-questions`、`banned-word`、`advice-form`、`contrast-ending`、
      `not-chinese`、`empty`。每条规则各有**独立**用例（`RULE_BREAKERS` 循环 9 条），
      免得一条规则失效被另一条还生效的规则盖住。
- [x] 校验失败时恰好重生成一次；第二次仍失败则输出**降级的安全回应**，且该回应自身通过全部机械校验。
      → `replyInto()` 最多问两次（`REPLY_ATTEMPTS = 2`），第二次把 `violations`（违反了哪几条）一并告诉
      provider；再失败就保持落库时那条安全线。测试断言 `provider.seen.length === 2`（不是 3），
      并对用户实际看到的那一句逐条复核：长度、句数、禁用词、转折、中文。
- [x] 假 provider 提供一个「故意违反回应规则」的脚本，测试用它走通「校验 → 重生成一次 → 降级」整条路径。
      → `REPLY_THAT_BREAKS_THE_RULES`（`src/domain/fake-provider.ts`），一句里同时犯四条：以「你为什么」
      起问、亲昵称呼「宝贝」、禁用词「别想那么多」、「不过…至少」转折收尾。另外给假 provider 加了
      `respondAttempts`（按第几次调用选脚本）——没有它就走不通这条路径。
- [x] 回应一律为中文。
      → `not-chinese`：必须含汉字，且不得含拉丁字母。用例：provider 回 `Got it, noted down.` → 被拒并降级。
- [x] 需要判断的规则（是否先接情绪、是否在给建议、是否贴标签、是否替用户做决定、是否做未被索取的提醒、
      是否把话题转向「开心的事」）通过写进 AI provider 的指令来约束，并由测试对**行为性质**做断言。
      → `REPLY_INSTRUCTIONS`（12 条，提炼自 `docs/ytwins/parent-voice-principles.md`）随每次请求发出；
      `RespondRequest.situation` 把机械读出的处境（含情绪 / 请求停止 / 明确问了怎么办）一并交给 provider。
      测试断言的是**行为性质**：provider 被告知了什么、用户最终看到的是哪一句、违规的那句有没有出现过 ——
      不断言 prompt 文本，也不假装能验证模型真的先接了情绪（边界写在下面「没能做成机械的那几条」）。
- [x] 用户说「不想说 / 算了 / 没事」时停止追问，只留一句最短的在场声明。
      → **这是结构保证，不是字符串校验**：`replyInto()` 在 `stopRequested` 时直接返回，provider **根本不会被问**，
      所以用户拿到的就是「嗯，我在。想说了再说。」（principles 规则 9 的示范台词）。测试断言
      `provider.seen` 为空 —— 也就是说那句「你想说说吗？」连被拒绝的机会都没有，它压根没被生成过。
      第一版只做到「回复里出现问号即违反」，被 `/code-review` 判为半个保证（「在场」读不出来），已改成现在这样。
      `REPLY_INSTRUCTIONS` 里那条停止追问的指令留着：词表漏掉的停止表达（例如「不想提」）仍要靠模型自己收敛。
- [x] 只有用户明确问「怎么办」、或用户自己已说出一个方向时才给建议，且最多一条。
      → 「明确问了」是机械的（`adviceRequested`，词表 `ADVICE_CUES`），随 `brief` 交给 provider；
      「自己说出了方向」是判断，写在指令第 4 条里。机械这一侧的抓手是规则 5：`advice-form` 禁掉
      「你应该 / 你得 / 你必须 / 我建议 / 建议你 / 你最好」——建议必须说得可以谢绝。

## Comments

### 2026-09-15 — 两轴 `/code-review` 之后的修订

两轴都找出了真问题，全部已改。下面是**改了什么**与**为什么有两处不改**。

**Spec 轴。**

1. **「只留一句在场声明」原来只硬到「不问」。** 校验只拒问号，所以「好的，我记下了。」这种既没问号、又不是在场
   声明的句子会**覆盖**掉降级线并被展示。改成结构性保证：用户请求停止时 `replyInto()` 不调 provider，
   答的就是那句在场声明。代价是 `ReplySituation` 里多了 port 用不上的第三个读法 —— 所以 port 的类型收窄成
   `ReplyBrief`（两个读法），转换只发生在 `briefFor()` 一处；把模型不该被问的事发过去让它「别说什么」，
   比不发更糟。
2. **`question-when-emotion-first` 与 `empty` 没有独立用例。** 原来只有那个「一次犯四条」的脚本碰到它们，
   把校验删掉测试照样全绿 —— 与「每条规则各有独立用例」自相矛盾。现在 `RULE_BREAKERS` 带可选的
   `body` / `expected`，两条规则各补了一条只犯自己的用例。
3. **词表是纯子串匹配，普通输入会被误判。** 「明天下午三点开会，有点麻烦」里的「烦」、「哪怕下雨」里的「怕」、
   「我算了算时间」里的「算了」都会命中，于是普通投递被回一句情绪回应、甚至**根本不被送去 provider**。
   加了一层 `LOOKALIKE_WORDS`（麻烦、烦琐、烦请、累积、累计、哪怕、恐怕、算了算）：匹配前先去掉这些形状，
   再找 cues。代价是没做分词，判据写在代码注释里；换来的是「不含情绪的投递不硬凑情绪回应」真的成立。
   三种误判各有一个用例，并且断言 provider 被问了。
4. **一条断言的消息写反了。** 原来写「the user was shown the line the provider offered」，而它断言的是
   *没有* 被展示。已改成「the user was shown X, which the rules refuse」。
5. **页面注释承诺了一件代码没保证的事。** `settleDrop` 一读到 `extracted` 就停，而措辞是另一个独立的后台任务，
   所以表单上方那句可能还是安全线、列表里却已是替换后的那句。现在读取完成后另给措辞 4 轮（1 秒）宽限，
   用 POST 返回的那句当「还没被替换」的标记；宽限用完就照实显示，那句也是真的。

**Standards 轴。**

6. **三行只有中文的注释**（`parent-voice.ts` 的禁用词分组）违反 `AGENTS.md`「代码注释保持英文」，已改英文。
7. **`tools/e2e-ticket-03.mjs` 与 `docs/agents/workspace-layout.md` §`tools/` 晋升规则 1 冲突**（只服务一个
   effort 的脚本应进 `archive/`，而 `archive/` 不进 git）。已在规则原文里补上**唯一一个已命名的例外**：
   `tools/e2e-ticket-<NN>.mjs` 是**回归**（每改一次领域代码就重跑一遍跨层链路），不是「当时跑过什么」的记录，
   所以留在 git 里；`tools/README.md` 改成引用那一节。规则 1 对别的脚本照旧。这条同时把 ticket 02 留下的
   同一处漂移补上了。
8. **规则名是自由字符串**（既当返回值、又当重试载荷、又被测试断言）—— 拼错会静默让一条规则永不生效。
   收成 `ReplyViolation` 联合类型；port 那边仍是 `string[]`，因为 port 只把它们当不透明的标签转发。
   同时并掉 `WHY_OPENINGS` / `WHY_PHRASES` 两份「问为什么」的清单，改成一份 contains 检查。
9. **`'听起来今天挺累的。'` 在测试里写了两遍**（一处内联、一处 `GOOD_REPLY`）—— 少写一份的代价是那个
   早先的断言会绕过常量，所以把 `GOOD_REPLY` 提到文件顶部，两处共用。
   `parent-voice.ts` 的安全线与假 provider 的默认回应原来**是同一句**「接住了。」，现在默认改成「记下了。」：
   两者重合就分不清「代码兜底」和「provider 答的」，而且会让页面的宽限轮询白等。
10. **`safeReply(readSituation(...))` 在两处重算** —— 收成 core 里的 `safeLineFor(body)`。

**没能做成机械的那几条（更新）。** 判断类规则仍是「指令 + 处境送到 + 能机械判的部分挡住」，真实效果要等 12 换成
真 provider 才看得到 —— 用假 provider 断言「模型会先接情绪」是自证。上面第 1 条**不再是**这个清单的一员：
请求停止现在是结构保证。

**没有进 `CONTEXT.md` 的新词。** `ReplyBrief` / `ReplySituation` / `violations` 是 port 与实现层的词汇，
不是产品词；产品词是 `CONTEXT.md` 里已有的「回应方式（parent voice）」。假 provider 默认回应从
`接住了：${body}` 改成「记下了。」是这一张的连带结果（回声会超出长度上限），不是顺手改的。

**两处被指为「超范围」，一处接受、一处不改。** 假 provider 默认回应的改动见上（是连带结果，已记）。
`RespondRequest` 拆出 `ExtractRequest` 不改：给 `RespondRequest` 加了 `brief` 与 `instructions` 之后，
`extract` 若继续共用这个类型，就得收下一份它用不到的处境与指令 —— 那才是真的把两件事混在一起。
拆开是这一张改动的直接后果，不是顺手扩张。

### 2026-09-15 — 实现完成

**这一张做了什么。** 回应成为**投递自己的属性**（`drop_.reply`），不是页面上的「最后一句」：刷新之后要看到
同一句话，而这是「接住」的一部分。仓库里因此有两条线，它们的关系是这一张的核心：

- **落库那一刻**，投递拿到一条**代码自己担保**的线（`safeReply()`：请求停止 → 在场声明，含情绪 → 情绪回应，
  其余 → 记录确认）。三条都短、都是中文、都过全部机械校验 —— 所以「投递永不沉默」不需要等任何人。
- **provider 答完并过了校验之后**，这条线被替换（`respond` → `checkReply` → `store.recordReply`）。
  这是**唯一**能覆盖它的路径：违规内容到不了用户面前，是被代码挡住的，不是被请求礼貌地要求别发的。

**没有改动的形状。** `drop()` 仍然不等 provider —— 01 立的规矩，02 沿用，这一张继续沿用。测试里因此改了
一处断言：原来钉死 `result.reply === '接住了。'`，现在钉「provider 给的那句**没有**回到这里」。同样能证伪
「没等」，而且不再把一个占位文案变成契约（那句话现在是**降级线**，会有别的场合合法地出现）。

**两条线怎么分。** 「代码校验」与「写进指令」的分界不是随手划的，判据是**这句话能不能从字符串读出来**：

- 读得出来的（句数、字数、问号数、「为什么」起问、禁用词、亲昵称呼、转折收尾、有没有中文）→ `checkReply()`。
- 读不出来的（这一句是不是情绪回应、是不是在给建议、有没有贴标签、有没有替用户做决定）→ 进
  `REPLY_INSTRUCTIONS`，并靠 `brief` 把处境一起送过去；测试只断言能观察到的那部分。

**几个不显然的决定。**

1. **重试要带上 `violations`。** 不带信息的第二次请求等于重摇一次，模型没有任何理由比第一次更对。
2. **请求停止优先于情绪，而且整轮不问模型。** 「算了，好烦」拿到的是在场声明 —— 对方已经在往后退了，
   这时候替他命名感受是把人拉回来；这种时刻也不该由模型去够一句漂亮话。
3. **情绪词表刻意不含单独的「气」「崩」。** 「天气」「崩塌」是日常词，误判的代价是给一段平平常常的话
   硬加一句情绪回应。长一点的形态（生气、气死、崩溃）覆盖了规则本来要的那几个意思。
4. **机械这一侧不判「有没有给建议」。** 规则 4 允许「用户自己说出了方向」时给建议，而这件事读不出来；
   能硬判的是规则 5（建议必须可以谢绝），所以 `advice-form` 只禁祈使句式，不禁「给建议」本身。
5. **没有给回应加「补跑」入口。** 抽取有 `extract(dropId)`（ticket 02 明确要求），回应没有：票面没要求，
   而那条线永远存在（兜底线就是它），所以加一个入口属于为想象的需求做抽象。12 换真 provider 时如果
   需要，再带着真实理由加。

**兼容旧库**：`ensureColumn` 给已存在的 `drop_` 补 `reply TEXT`（可空）；读回 NULL 时核心按正文重算安全线
（`toSummary`）——「这条投递很旧」和「这条投递没有回应」是两件事，前者不该显示成后者。手工验过一次
（建 01 的旧表 → 用新 store 打开 → 旧行读出正确的安全线），没写成测试：那要断言 SQL 表结构，而本仓库
的测试只从领域 interface 驱动，02 的同一处迁移也没测。

**页面**：每条投递下面显示它自己的回应（`renderDrop`），所以刷新之后看到的是当初那句；投递完成后
`settleDrop` 把读回来的那条返回，表单上方那句随之更新。CSS 只加了一个 `.drop-reply`。

**测试与验证**：领域 **61/61**（新增 20 条，全部走领域 interface + 假 provider）；`tools/e2e-ticket-03.mjs`
**6/6**（新增，真 HTTP：落库那条 → 替换那条 → 违规那句在任何响应里都取不到 → 请求停止根本不进 provider
→ 重启后同样）；`tools/e2e-ticket-02.mjs` 7/7 仍全绿；`check-workspace` 21/21、`tsc --noEmit` 全绿、
`vite build` 成功。真实服务器手工过了一遍第一幕：丢 demo 片段 → 立刻「听着今天不太好受。」→ 落成
「听着，事情全堆在一起，心里挺堵的。」；「明天下午三点开会」→「接住了。」；「算了，不想说了」→
「嗯，我在。想说了再说。」。
