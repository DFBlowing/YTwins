# 08: 排程 —— 事项落到时间上

**What to build:** **事项**被自动落到时间上，用户不用自己填时间。页面上能看到即将到期的事项列表，
打开页面就知道该做什么；没有解析出时间的事项留在「待安排」，而不是被丢掉。

**Blocked by:** 02（接住的结构 —— 自动分出事项与留档）

**Status:** ready-for-human

- [x] 含时间信息的事项被自动落到具体时间上，用户无需手工填写。
      → `dueAt` 仍由 provider 在**抽取**时报出（02 定的形状），08 负责把它**落到时间上**：
      新增 `domain.upcoming()`（`src/domain/scheduling.ts` 的 `upcomingFrom()`），按时刻排序成**到期**列表。
      页面上没有任何填写时间的控件，用户全程不必输入。解析本身不归 08 —— 那是 provider port 的事，
      01–11 全跑假 provider，真实现的解析质量是 12 的事（`ai-provider.ts` 的 `ExtractedItem.dueAt` 写明「没时间就说没有，不要编一个」）。
- [x] 没解析出时间的事项保留为「待安排」，不被静默丢弃。
      → `Upcoming.unscheduled`，与 `due` 分列两表。`dueAt` 为 null **或**`Date.parse` 读不出来的，
      都进这一列而不是被丢掉 —— 读不出来的时间不算时间，否则它会排在时间线最前面挂着一个渲染不出的日期。
- [x] 页面按时间列出即将到期的事项，以及单独的待安排列表。
      → 第一幕顶部新增「接下来要做的」一节（`/api/upcoming`）：到期在前、待安排在后，各有空态文案。
      **过期的排在最前**（`已过期 · …`），不是被过滤掉 —— 它是当下最该做的一件事。两列而不是一列：
      有时间与没时间是两件不同的事实，合成一列等于给后者硬编一个顺序。
- [x] 事项的状态可被推进（例如从待办变为已办），且该状态在刷新后仍然保留。
      → `ItemState = 'todo' | 'done'` + `domain.setItemState()` + `POST /api/items/:id`；
      `item_.state` 落库（`NOT NULL DEFAULT 'todo'`），重启后仍成立。可**撤销**（done → todo）：
      点错了要能改回来，「已办」是用户更正的事实而不是他做过的承诺。
      **已办的事项从两个列表里都消失**（两个列表答的都是「还剩什么要做」），但**仍然是事项**：
      `listItems()` 里还在，`dueAt` 也还在 —— 消失的是追问，不是事实。
- [x] 排程不引入完整日历 UI，也不做冲突检测。
      → 没有月历、没有时长、没有日期选择器；两件同一时刻的事项就是两件同一时刻的事项，
      `upcomingFrom` 全程不比较事项之间的关系。`tools/e2e-ticket-08.mjs` 用两件同一时刻的事项把这条钉住了。
- [x] demo 阶段不做系统级推送与提醒可靠性保证。
      → **明确地没有做提醒**，见下「提醒的含义被收敛成了什么」。

## Comments

**2026-09-17 — 实现完成**

**新增的领域词汇与形状**（`src/domain/interface.ts`，最高 seam）：

- `ItemState = 'todo' | 'done'` 与 `ITEM_STATES` —— 两个值而不是一列可选状态。产品不向用户要任何东西，
  所以没有「进行中」「优先级」「分类」，也不会有；唯一的动作是「做完了」。`_Avoid_` 里的「待办／任务／todo」
  仍然不出现：领域里它叫**事项**。
- `Item.state` 新增；`Upcoming { due, unscheduled }` 新增。
- 新操作两个：`upcoming()`（**排程**：还剩什么要做）与 `setItemState(itemId, state)`。

**三个设计决策值得记下来：**

1. **`upcoming()` 返回两个列表，不是一个列表加一个布尔。** 有时间与没时间是两种不同的事实，
   合成一列会强迫页面给第二类编一个顺序，或者把它们藏到第一类后面 —— 而「不被丢掉」正是这一节存在的理由。
2. **时间由域读一次，再传下去。** `core.ts` 读 `now()` 一次交给 `upcomingFrom(items, at)`。
   域本来就拥有时间（`createDomain({ now })`），一次读取里问两次时钟会让同一张列表对着两个时刻排序。
   注意：`at` 目前**只用于统一时刻，不做过滤** —— 过期事项照常列出（且排最前），这是有意的。
3. **`item_.state` 的迁移带了默认值，别的列没有。** `ensureColumn(db, 'item_', 'state', "TEXT NOT NULL DEFAULT 'todo'")`
   —— 因为有一条规则在读它（`upcomingFrom` 只收 `todo`），旧库里留成 NULL 会让这个文件**原本就有的事项全部隐形**。
   02–07 写的库都由此升级；`domain.test.ts` 里手工造了一个没有该列的旧库来钉住这条。

**提醒的含义被收敛成了什么（这一条要写清楚，别让下一张 ticket 以为提醒做过了）。**
`CONTEXT.md` 的**排程**词条写的是「把事项落到时间上，并在到点时提醒」，ticket 的 What to build 也用了「提醒」。
本次**没有做任何形式的提醒** —— 既没有系统级推送，也没有页面内的提示。`NEXT.md` 指示把这个词的含义在 08 里
收敛成页面内的东西，spec 的「不在范围内」又排除了系统级推送与提醒可靠性，两条合起来得到的产物是一张
**打开页面就能看懂的列表**：正确的顺序、过期的最前、待安排的另列。这满足了「打开页面就知道该做什么」，
但没有满足「到点时提醒」，是**主动放弃**而不是遗漏。真要做出提醒，得先回答 demo 阶段凭什么保证它在到点时会响。

**审查（`/code-review` 两轴）发现并已修的三处：**

1. **待安排那一列的死按钮**（Spec 轴）。`renderScheduledItem(item, false)` 照常画出「未办」按钮，
   但只有 `dueList` 挂了监听，`unscheduledList` 一个都没有 —— 待安排里每一行都渲染了一个按下去没反应的按钮。
   已改为两个列表共用同一套委托监听（`scheduleLists`），并在 e2e 里补了「没有日期的事项也能推进」一条。
2. **`ITEM_STATES` 声明了两份，`interface.ts` 那份没人 import**（Standards 轴，Duplicated Code）。
   其余词汇（`INPUT_TYPES`、`LINK_KINDS`、`CONCLUSION_TIERS`）都只在 `interface.ts` 里，
   已删掉 `scheduling.ts` 的副本、改为 import。
3. **`DropResult.dropId` 是无主的投机抽象**（两轴都点了，Speculative Generality）。
   它是给 11 预备的，但本次**没有任何调用方读它**，值恒等于 `id`，而它的注释还在用「记录与投递还区分不开」
   来为「先把它加上」辩护 —— 循环论证。这正是同一个 interface 的注释里明说不做的事
   （「不会预先声明 stub 来假造行为」）。已删除；11 真的要它时再加。
   （另修了一处小重复：`dueLabel` 与 `formatDue` 各写了一遍「时间用不了」的判断，抽出 `dueMoment()`。）

**没有踩的两件事**：没有引入日历或冲突检测（e2e 显式钉住）；`date-only` 的 `dueAt` 也排序正确 ——
按**时刻**而不是按字符串比，`2026-09-23` 与 `2026-09-23T09:00Z` 这种同日不同写法才不会被字符串顺序骗到。
