- **09 已实现**，`Status: ready-for-human`：**删除 —— 先告知，再级联**。两个操作而不是一个：
  `previewDeletion(dropId)` 报出「有 N 条小结论是从它来的」——报的是**小结论的原话**（`ConclusionRef[]`）
  而不是一个数字，只报数字是让用户去信一个统计；`deleteDrop(dropId, mode)` 执行，
  `mode` 三取一且**必填**（`'cascade' | 'original-only' | 'keep'`），`'keep'` 什么都不删 ——
  所以「静默删除」在调用形状上就不可达。API 同理：`POST /api/delete` 不给 `mode` 是 400。
  第一幕每条投递旁多一个「删掉这次投递」按钮，点它**不删任何东西**，只是把预览摆出来由用户选。
  **两个口径写清楚了**：① `original-only` 选的是「**保留**」而不是「标记失效」—— 画像是一份当时怎么想的
  历史，改写旧结论是产品修改自己的过去，理由在 ticket 09 的 `## Comments`；② 「共享词条」不放行字面要求 ——
  `term_` 一个写法一行，删掉「只有这次投递说过」的，**被别的投递也说过的不删**，否则等于悄悄改写用户没删的内容。
  **本次唯一的 schema 改动，也是本次最值钱的教训**：`term_.origin_drop_id` 的 `ON DELETE CASCADE` 是错的 ——
  这条引用不是唯一撑着该行东西（多条投递都 mention 同一个 term），删一次投递会把「好烦」从别的投递嘴里拿走。
  已改成**不带外键**并加了重建表的迁移（`dropTermOriginCascade()`），细节见 `sqlite-store.ts` 的 schema 注释。
  **另一处坑**：第一版 `reopenMatter` 往 `matter_drop_` 插了一行指向不存在投递的合成记录，每次抛
  `FOREIGN KEY constraint failed`（`original-only` → 500），而领域测试**全都够不到**那个分支
  （锚点是「好烦」，三条投递都说，重锚路径从没被走到）—— 是 `/code-review` 的 Spec 轴查出来的。
  已补两条检查（含专钉「锚点被孤立」的分支，并实测把 bug 放回去它就红）。

  `markConclusionWrong(conclusionId)` 只往 `conclusion_` **追加**一行（`kind: 'correction'`、
  `relation: 'overturn'`、`supersedes` 指向被否的那条），旧结论一字未改 —— 全程没有一句 UPDATE / DELETE。
  那条记录的话**由代码写死**（`CORRECTION_LINE`「你标了这条不对。」），**不花模型**：用户刚说这条看错了，
  让模型写一版「修正后的说法」等于借这次否定再编一条关于用户的判断。重复标只记一次。
  **「标不对」还走到语料层**（05 的 prototype 决定第 5 条，清单里没列、开工前问过作者要做）：被否的那件事
  按 `overturnedOverlapFactor`（0.3）打折 —— 阈值 0.50、重合上限 1，所以打折是**决定性的**，猜不进去；
  再说话时档位退一档（`overturnedBandDrop: 1`），**退档这件事落在结论上**（`conclusion_.softened`）并由页面
  说出口 —— 三个数值一个字不改，否则「弱档」会和旁边那组本该是中档的数互相打脸。
  `appendToConclusion(conclusionId, body)` 复用 `drop` 的整条
  路径，并给那次投递带上 `pinned_matter_id`（新的一列，`ON DELETE SET NULL`、带迁移）：**写在旁边就是
  用户说的「这是关于这件事的」**，归并不再靠猜 —— 否则在上面那条降级下，这句话会飘到另一件事里去。

## 串行推进（2026-09-15 更正）

**之前这里写着「01 之后 02 与 07 并行；02 之后 03 / 04 / 08 并行」—— 那是错的，已删除。** 错在把「没有
blocking 边」直接当成了「可以并行」。这两件事不是一回事：

> **没有依赖 ≠ 可以并行。** 并行需要同时满足两条：① 依赖上无约束（没有 blocking 边）；② **文件上不相交**
> （两边动的是互不重叠的文件集合）。

02 与 07 都只依赖 01，所以满足 ①；但它们都从 01 的同一份状态出发，往**同一批文件**上扩张 —— 领域核心的
interface、AI provider port 的形状、存储 schema 的初始化、server 路由、页面骨架，01 里都只是刚好够第一幕
跑通的**最小**版本，02 要加「投递 → 事项/留档/词条」，07 要加「追溯提问」，改动落点高度重叠。两个 agent
同时干就是互相覆写，后完成的覆盖先完成的。`03` / `04` / `08` 同理（12 需要 03 与 04 都完成这条边，
本身就说明 03、04 会撞）。

**所以本 effort 一律串行。** ticket 刻意不写文件路径（路径腐化快），因此「文件是否相交」在 ticket 层面
**无法判定** —— 与其猜，不如不并行：这是个人项目、单 agent 顺序干，串行的代价接近零。

**将来真要并行时的规矩**（本次不适用，留作后续约定）：只有当两边的改动**天然分居不同子系统**、文件集合
可判定不相交时才列并行；做不到就二选一 —— 要么不列并行，要么给并行方各开一个**临时目录**分别存放，
等其中一方最后完成，再单独做一次**合并**（合并本身是手工活，不是零成本）。

## 已冻结的决定（不要再问一遍）

- **demo = 三幕**（2026-09-14 确认；将来用实践检验是否增减）：
  ① **丢** —— 往输入框丢一段无格式的杂乱输入（含老师讲的评分标准 + 一句情绪），不选类型、不填时间，

  ③ **浮** —— 再丢一句情绪化输入，浮出一条**不确定语气**的小结论（用预置的足够词条支撑）。
